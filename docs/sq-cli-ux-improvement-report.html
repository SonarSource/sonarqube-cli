SonarQube CLI UX Improvement Report

How to simplify setup, communicate value, and reduce the knowledge barrier — informed by LeanCTX patterns and the current SQ CLI architecture.

Date: July 8, 2026 Scope: UX, onboarding, integrate flows Goal: Easy setup without deep product knowledge

Executive Summary

SonarQube CLI is powerful but fragmented. Users must understand authentication, project keys, six agent subcommands, global vs project scope, feature tiers (MCP, secrets, SQAA, CAG, git), and entitlement gates before they capture full value.

LeanCTX succeeds with a single golden path (lean-ctx onboard), self-healing diagnostics (doctor --fix), and value before vocabulary.

North Star

A new user in a repo with Cursor installed should reach “Sonar protects my AI workflow” in three commands: 

sonar auth login
sonar onboard
sonar system status

Key finding

SQ CLI’s integration engine is ahead of LeanCTX (declarative, scoped, entitlement-aware, stateful). The UX layer is behind (no golden path, no batch setup, no self-heal, jargon-heavy quickstart). The fix is mostly orchestration and copy, not new features.

Current User Journey — Pain Points

What sonar --help tells users today

QUICKSTART
  1. Run sonar auth login to authenticate with SonarQube
  2. Run sonar analyze --file <file> to scan your code for issues
Issue Impact
Integrate missing from quickstart Main AI value prop (hooks, MCP, SQAA) not in first steps
analyze --file as step 2 Assumes manual scanning; most users want agent-integrated quality
No “am I done?” step Nothing points users to sonar system status

Integrate flow friction

Step Friction
sonar integrate Pick one of 6 tools from a flat list
Per agent Full preflight + scope prompt + per-feature confirms
Terminology “Vortex agentic analysis”, “Context augmentation”, MCP, hooks
Scope User must understand project vs global before knowing what each enables
CAG / SQAA skips Warn lines easy to miss; users don’t know why features didn’t install
Multi-agent setup New agent = rerun entire flow; no “wire all my tools”

Knowledge users are expected to have

  • Project key sources (sonar-project.properties, .sonarlint/, --project)
  • Which agent they use and its subcommand name
  • Global vs project scope (SQAA/CAG are project-only)
  • --dependency-risks requires -p and can’t be global
  • sonar context requires prior integrate + entitlement
  • Difference between analyze, analyze agentic, analyze secrets, analyze dependency-risks

That’s too much for “easy setup.”

What LeanCTX Does Well

LeanCTX Pattern SQ CLI Application
onboard — zero-prompt, all detected tools sonar onboard — all detected agents + optional git
doctor / doctor --fix sonar doctor --fix or extend system status
Setup tiers (Minimal / Standard / Full) Presets: --minimal, default, --full
Per-agent installation matrix Publish “what files we touch per agent”
Clear next steps after setup “Restart Cursor → try sonar list issues -p …”
Non-invasive defaults Default project scope; batch non-interactive install
Continue-on-error in batch setup One agent fails → others still install

LeanCTX model

One wiring model per agent. MCP + hooks + optional rules/skills. No global vs project split for features.

SQ CLI model

Two axes: invocation scope (project/global) + per-feature scope pins. SQAA, CAG, git dependency-risks are project-only by design.

Implication for batch onboard

sonar onboard --global is valid but intentionally thin (MCP + secrets). Full AI analysis requires a project-scoped run. This must be explained at decision time, not via post-hoc warn lines.

What SQ CLI Already Does Well

  • Declarative integration registry — idempotent installs, state tracking, post-update refresh
  • Managed markers — safe re-runs without clobbering user edits
  • Preflight summary — connection/project validation before install
  • remediationHint on errors — extend usage across more paths
  • sonar system status --json — foundation for doctor/repair
  • --non-interactive — auto-accepts feature prompts (underused for onboarding)
  • Global secrets dedup — avoids duplicate hooks across scopes
  • Post-update migrateDeclarativeIntegrations — upgrades don’t orphan config

P0 — Onboarding & Golden Path

P0

1. Add sonar onboard

The single highest-impact change.

sonar onboard
  → detect installed agents (Cursor, Claude, Codex, Copilot, Antigravity)
  → detect git repo (optional checkbox)
  → ONE scope prompt (default: this project)
  → ONE entitlement check (SQAA, CAG)
  → install all selected agents with --non-interactive
  → rollup summary + next steps
Mode What gets installed
Default (project) Full stack: MCP, secrets, SQAA (if entitled), CAG (if entitled), git hooks
--global Thin stack: MCP + secrets; banner that SQAA/CAG need project re-run
--minimal MCP only — data access first

Reuses existing guards in resolveSqaaSetup and resolveContextAugmentationSetup. Requires extracting shared preflight from displayAgentIntegratePrelude() and fan-out to existing handlers.

P0

2. Rewrite root quickstart

QUICKSTART
  1. sonar auth login
  2. sonar onboard              # set up your AI tools (from repo root)
  3. sonar system status        # verify everything is wired
P0

3. Post-auth “what’s next” nudge

After sonar auth login, if cwd looks like a project:

✓ Authenticated as SonarQube Cloud (my-org)

Next: run sonar onboard from your project directory to connect your AI tools.

P0 — Diagnostics & Self-Healing

P0

4. sonar doctor with --fix

Check Fix action
MCP config invalid/missing Re-apply from state (migrateDeclarativeIntegrations)
Hook script points to old sonar path Regenerate hook scripts
SQAA rule marker missing Re-render managed rule
CAG skill stale Refresh skill (post-update path)
Auth token invalid sonar auth login
No integrations at all sonar onboard 
sonar doctor                  # human-readable per-agent health
sonar doctor --fix            # repair from state, no re-prompts
sonar doctor --json           # CI gate
P0

5. Hook binary path refresh on self-update

Verify generated hook scripts reference current process.execPath after sonar self-update. Stale paths are the primary silent failure after upgrades.

8. Scope explained at decision time

Where should SonarQube be integrated?

  ● This project (recommended)
    → AI code review, context augmentation, project MCP
  ○ Global (all projects)
    → MCP + secrets only; re-run from a project for full AI analysis
P1

9. Project key: discover silently, explain when missing

One guided path when discovery fails — not three paragraphs in every subcommand’s --help. Onboard attempts discovery once and shows the resolved key in preflight.

Target Experience (v2)

Install sonar → sonar auth login → sonar onboard → Restart AI tool → sonar system status → Use agent normally

User knowledge required: “I use Cursor” (optional — we detect it). Not: MCP, scope, SQAA, CAG, hook events.

Bottom Line

Do

  • sonar onboard — one command, project scope, all agents
  • sonar doctor --fix — broken setup recovers itself
  • Presets + plain language — users choose outcomes, not feature IDs
  • Quickstart: auth → onboard → status

Don’t

  • Remove per-agent subcommands — onboard is the front door
  • Hide global/project — explain once at onboard
  • Auto-install without preview — one aggregated confirm box
  • Rebuild LeanCTX — partner via addon

Phase 1 (sonar onboard + quickstart rewrite) is the best place to start — highest leverage, reuses almost all existing integrate infrastructure.

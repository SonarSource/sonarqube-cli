# Declarative integration framework

The declarative-integration engine lives under `src/core/framework/` — it has no CLI-specific coupling, so it sits alongside `src/core/host/` rather than nested inside it: `src/core/framework/features/`, `src/core/framework/resources/`, and `src/core/framework/dependencies/` (including the generic SonarSource binary dependency) as sibling modules. New integration descriptors should import from `@/core/framework/features` for dependency/resource factories, operations, and registry validation. Command handlers should keep command-specific validation, prompts, and target resolution thin, then delegate feature selection, generic install messages, dependency/resource application, and state recording to `src/core/framework/features/install-integration.ts`. Only the CAG binary dependency declaration stays in commands, at `src/commands/integrate/_common/context-augmentation-dependency.ts`, since it calls the SonarQube API clients and CLI output helpers.

Resource removers delete an emptied file instead of leaving a husk: `text-snippet` when only whitespace remains, patch removers (`json-patch`/`yaml-patch`/`toml-patch`) when the document prunes (via `pruneEmptyContainers`) to its `defaultValue`. User/other-feature content survives pruning and keeps the file; empty parent dirs are left in place.

The registry supports a **container + subfeatures** model: a `FeatureContainer<TOptions>` (extending `FeatureDeclaration`) owns the centralized resource and declares a `subfeatures: SubfeatureDeclaration[]` array. A subfeature owns its own `dependencies`, `resources`, and `operations` but inherits the container's scope, target root, and attrs; resource and operation ids must be unique across the container plus all its subfeatures. Use `isFeatureContainer` (`@/core/framework/features/types.ts`) / `selectActiveSubfeatures` (`@/core/framework/features/selection.ts`) to downcast and evaluate subfeature conditions. Active subfeatures are carried on `FeatureApplication.activeSubfeatures` through the pipeline and recorded nested under `InstalledIntegrationFeature.subfeatures` in state, each with the `resources` / `operations` it applied (both absent in state written before subfeatures owned assets). Read a feature's full asset set with `recordedFeatureResources` / `recordedFeatureOperations` rather than `feature.resources` / `feature.operations`, which hold container-declared assets only. Removing a container removes container and subfeature assets alike; a subfeature that is no longer active on re-run has its recorded resources removed and its undoable operations reversed. Binary dependencies declared by active subfeatures are collected and installed alongside container deps.

`IntegrationInvocation.resolvedFeatureDecisions` (a `Map<string, FeatureSelectionOutcome>`) lets a top-level feature's `shouldInstall` read an *earlier* sibling's just-resolved decision instead of independently re-deriving one from raw options and risking disagreement — `selectFeaturesForInvocation` populates it, keyed by feature id, immediately after each top-level application's decision resolves (before that feature's own subfeatures are evaluated, so a container's subfeatures always see their own container's entry too). This only works for a feature declared *after* the one it depends on in the integration's `features` array; declaring it before means the dependency isn't resolved yet, so the reader falls through to whatever fallback it defines. `vortexInstallDecision` (`integrate/_common/vortex.ts`) is the one real usage: Claude's `PostToolUse` dispatch container reads the `vortex` container's resolved outcome this way, which is why `createVortexFeature` must be declared before it in `claude/declaration.ts`.

# Stats

A local-only SQLite ledger (`{SONAR_USER_HOME}/sonarqube-cli/db/stats/stats.db`) recording one row per analyzer run (secrets, SQAA, SCA), for accuracy metrics only — nothing here is ever transmitted. The fact lifecycle mirrors telemetry's on purpose: handlers call `ctx.recordStats(new StatsFact(...))` (buffered on `CommandInvocationContext`, `src/core/commands/invocation-context.ts`) and `postAction` (`command-tree.ts`) drains the buffer via `commitStatsFacts` — synchronous, no queue/flush, per the CLI-1112 ADR. Not gated on telemetry consent (`isTelemetryEnabled`) — CLI-1114 will add a dedicated stats on/off flag; don't gate on the telemetry one in the meantime.

`facts.ts` is the only entry point producers use: `buildStatsFromTelemetry(fact, details)` takes the `TelemetryFact<AnalysisCompletedPayload>` a producer already built for `CliAnalysisCompleted` and reads `caller_command`/`analyzer`/`exit_code`/`scan_duration_ms` straight off its payload (via the structural `AnalysisFactEnvelope` type — not imported from `src/commands/analyze/analysis-completed.ts`, since `src/core` never imports `src/commands`; a value added to `AnalysisTelemetryAnalyzer` without a matching addition to `StatsAnalyzer`, `store.ts`, surfaces as a compile error at this call site, not silent drift). It is a pure builder — it does not touch `ctx` — so every call site follows `ctx.recordTelemetry(fact); ctx.recordStats(buildStatsFromTelemetry(fact, details));`. `details` is the only thing a producer supplies by hand: `findingsCount`/`ruleCounts`, computed by that analyzer's own dedup callback — secrets fingerprints new findings against the ledger (`buildSecretsFingerprint`/`summarizeNewSecretsFindings` in `src/commands/analyze/secrets-analysis-telemetry.ts`); SQAA/SCA pass raw, undeduped counts (approximate by design this iteration). `caller_command` → `run_trigger` (`manual`/`hooks`) classification is hand-synced against `SECRETS_CALLER_COMMANDS`/`SQAA_*_CALLER_COMMAND`/`SCA_CALLER_COMMANDS` for the same import-direction reason.

Hooks that call `process.exit()` directly (e.g. `denyCursor` in `src/commands/hook/cursor-secrets-block.ts`) bypass `postAction` entirely, so they must call `commitStatsFacts(ctx.statsFacts())` themselves before exiting or the buffered fact is lost — `ctx.telemetryFacts()` has the identical problem on that same path and is not yet handled the same way.

**`store.ts`** is the module producers call to write/read `stats_events`/`rule_descriptions`/`seen_fingerprints` day to day; `db.ts` (purge) and `migrations.ts` (schema, plus a one-time `stats_events` read for backfill) are the other two that touch these tables, both from the connection-lifecycle layer rather than as producers. `withDb` makes every ledger operation best-effort, mirroring `appendTelemetryEvent`: open/write failures are logged at debug and swallowed in favor of the caller's fallback (never new-findings-are-zero by accident — `dedupeAgainstSeen`'s fallback is "everything is new", not "nothing is new"). Four tables: `stats_events` (one row per run, `details` a JSON blob), `rule_descriptions` (rule key → message lookup, upserted independent of dedup), `seen_fingerprints` (scope + fingerprint, for `dedupeAgainstSeen`), `stats_aggregates` (see below). `recordStatsEvent` wraps the `stats_events` insert and (for `analyzer`-class events) the `stats_aggregates` update in one transaction, so a crash mid-write can't leave one without the other.

**`aggregates.ts`** (CLI-1115) owns all reads/writes of `stats_aggregates` rows — `migrations.ts` only creates the table (`CREATE TABLE`) and calls into `aggregates.ts` for the v2 backfill, it never touches the table with raw SQL of its own. `stats_aggregates` is an all-time rollup, keyed `(dimension, key)`, that survives purging old raw rows: `global` (totals, `runs_with_findings` for agent-hit-rate, `blocked` for secrets-blocked-total, `first_seen_ms`), `analyzer`, `agent`, `trigger`, `caller_command`, and `rule` (keyed `<analyzer>:<ruleKey>`, so `sonar stats`'s eventual `topRules`/`topSecretTypes` at `--since all` can still join rule keys back to `rule_descriptions`, which is never purged). `applyAnalyzerEventToAggregates` is a plain function over a self-contained input shape (not `store.ts`'s types) specifically so it stays a dependency-free leaf both `store.ts` (live writes) and `migrations.ts` (one-time backfill on upgrade) can import without a cycle. **Scope boundary**: only `event_class = 'analyzer'` rows feed aggregates — this mirrors the only concrete reader spec found (the abandoned `CLI-1040-sonar-stats-poc` branch's `stats-queries.ts`, which always joins on analyzer details). `tool`-class rows (CAG) are purged after a year with no aggregate preserved; add a `tool` dimension if a reader ever needs CAG history past the retention window.

**`db.ts`** opens the db WAL-mode with a 5s busy timeout, applies migrations, purges (`purgeOldStatsEvents`) `stats_events` rows older than `STATS_RETENTION_DAYS` (`config-constants.ts`, 365 days per CLI-1115's ADR), and quarantines (renames aside) a corrupted db before recreating it fresh — `PRAGMA busy_timeout` must be set _before_ `PRAGMA journal_mode = WAL`, since the WAL conversion itself takes a brief exclusive lock that only the busy handler can wait out. Purge runs unconditionally on every open (same place migrations already run) rather than from a dedicated command, so retention doesn't depend on a `sonar stats`/maintenance invocation that may never happen; it never touches `stats_aggregates`, whose rows are already fully incremented at write time. `isCorruptionError` only recognizes actual SQLite corruption codes (`SQLITE_NOTADB`/`SQLITE_CORRUPT`) — a db whose `user_version` matches but whose actual table shape doesn't (e.g. a stale schema from an earlier draft of a migration) is not detected as corrupt, and `withDb` silently swallows every subsequent write forever. Known gap, not yet hardened; matters most during active schema iteration, before a migration's shape is final.

**`migrations.ts`** — versioned, `up(db)` + bump `PRAGMA user_version`, wrapped in `.immediate()` (not the default deferred transaction) so two processes racing to create a brand-new db can't both read `user_version = 0` and collide on `CREATE TABLE`. `dedupeAgainstSeen` in `store.ts` uses the same `.immediate()` reasoning for its own read-then-write. `STATS_MIGRATIONS` is exported (only) so tests can apply a prefix (e.g. just v1) to set up pre-migration fixtures. Migration v2 creates `stats_aggregates` and backfills it from every pre-existing `analyzer`-class `stats_events` row, so upgrading an installation that already has history doesn't reset its all-time totals to zero the moment purging starts deleting rows.

**Testing**: `tests/unit/core/stats/_helpers.ts`'s `useTempSonarUserHome()` points `SONAR_USER_HOME` at a fresh temp dir per test. `tests/_common/stats-helpers.ts` has read helpers (`readStatsEvents`, `readStatsRuleDescriptions`, `readStatsAggregate`) for asserting on the ledger from both unit and integration specs, plus `readStatsAggregateFromDb` for tests that build their own `:memory:` database (e.g. exercising `applyAnalyzerEventToAggregates` or a migration's `up()` directly) rather than going through a file-backed `SONAR_USER_HOME`, and `removeTestSonarUserHome()` for the Windows-safe cleanup every test touching the ledger needs (WAL/SHM handles can outlive `db.close()` briefly on Windows).

**`stats-queries.ts`** (CLI-1113) is the read side — `queryStatsSummary(since)` for the `sonar stats` command (`src/commands/stats/index.ts`, documented in `src/commands/CLAUDE.md`). Everything above this line is the write/retention side these queries read from.

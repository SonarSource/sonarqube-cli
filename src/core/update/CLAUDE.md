# Self-update lifecycle

The global integration migration can retry in the `sonar update` command hook after its version gate has been spent. The retry happens before the command checks whether the running executable came from the standalone installer. Its warning recommends `sonar update` only for standalone installs. It directs externally managed installs to their original update method.

The post-command update notice uses the shared standalone installer location check. It recommends `sonar update` only at that path. Other installations receive guidance to update through their manager or original installation method.

The self-update lifecycle lives under `src/core/update/` — a top-level peer of `core/host/` and `core/framework/`, not nested inside either, because it legitimately depends on both. `post-update.ts` is the orchestrator, run once per upgrade from the command tree's root `preAction` hook — before Sentry init (so the legacy telemetry opt-out is migrated to config before Sentry reads it), and where `runtime.authResolver` is reachable, but not for `--help` / `--version`, which exit before any action; it calls the `*-migration.ts` modules beside it in sequence, and the order is load-bearing (see below). `post-update.ts` also defines `migrateDeclarativeIntegrations` directly (not worth its own file — it's a 4-line load/save wrapper) around `reconcileInstalledIntegrations` (`src/core/framework/features/reconcile.ts`), which owns the actual replay-declared-features-against-recorded-state logic — kept in framework rather than host/update so nothing under `core/host/` ever needs to import from `core/framework/`. See "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why `known-project-mappings-migration.ts` must run before `migrateDeclarativeIntegrations`.

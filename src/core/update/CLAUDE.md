# Self-update lifecycle

The global integration migration can retry in the `sonar update` command hook after its version gate has been spent. The retry happens before the command checks whether the running executable came from the standalone installer. Its warning recommends `sonar update` only for standalone installs. It tells externally managed installs that migration retries on the next CLI upgrade to a newer version.

The post-command update notice uses the shared standalone installer location check. It recommends `sonar update` only at that path. Other installations receive guidance to update through their manager or original installation method.

The self-update lifecycle lives under `src/core/update/` — a top-level peer of `core/host/` and `core/framework/`, because it depends on both. `post-update.ts` is the orchestrator. It runs once per upgrade from the command tree's root `preAction` hook, before Sentry init, so the legacy telemetry opt-out reaches config before Sentry reads it. It does not run for `--help` or `--version`, which exit before any action. It calls the `*-migration.ts` modules in order. `migrateDeclarativeIntegrations` runs slow feature reconciliation outside the state lock, then applies the resulting feature changes to the latest state through one `updateState` callback. `reconcileInstalledIntegrations` in `src/core/framework/features/reconcile.ts` owns the replay logic. See "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why `known-project-mappings-migration.ts` must run before reconciliation.

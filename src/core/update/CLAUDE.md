# Self-update lifecycle

The self-update lifecycle lives under `src/core/update/` — a top-level peer of `core/host/` and `core/framework/`, not nested inside either, because it legitimately depends on both: `check.ts`/`notification.ts` (version check and the post-command update notice), `post-update.ts` (the orchestrator run once per upgrade from `src/index.ts`), and four single-purpose migration modules `post-update.ts` calls in sequence — `telemetry-migration.ts`, `known-project-mappings-migration.ts`, `claude-hooks-migration.ts`, `binary-refresh.ts`. `claude-hooks-migration.ts` also owns the sonar-a3s obsolete-hook-artifact cleanup helpers (`OBSOLETE_A3S_MARKER`, `removeObsoleteHookArtifacts`, `cleanObsoleteFromState`, `migrateHookScripts`) — they're Claude-specific (hardcoded to `.claude`, not parameterized over agent or marker) and called directly by `commands/integrate/claude/index.ts` (manual re-run) and `post-update.ts` (top-level state cleanup) in addition to `migrateClaudeCodeHooks` in the same file, so a separate `migration.ts` wasn't earning its keep as its own module. `post-update.ts` also defines `migrateDeclarativeIntegrations` directly (not worth its own file — it's a 4-line load/save wrapper) around `reconcileInstalledIntegrations` (`src/core/framework/features/reconcile.ts`), which owns the actual replay-declared-features-against-recorded-state logic — kept in framework rather than host/update so nothing under `core/host/` ever needs to import from `core/framework/`. `known-project-mappings-migration.ts` runs deliberately **before** `migrateDeclarativeIntegrations` — see "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why the ordering matters.

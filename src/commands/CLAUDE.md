# Commands

The `hook/`, `context/` and `analyze/` handlers are the runtime half of the agent integrations that install them: `src/commands/integrate/CLAUDE.md` covers both halves and is the file to read before changing either.

To add a new command: add it to `createCommandTree()` in `src/commands/command-tree.ts` and implement the logic in a new folder under `src/commands/`.
Please declare commands using the type defined in `src/core/commands/sonar-command.ts`.
Lifecycle stages (`Stage`) live in `src/core/commands/stage.ts` and are re-exported from `sonar-command.ts`. Qualified invocation paths used in lifecycle warnings live in `src/core/commands/path.ts`.
By default, new commands should register a `authenticatedAction()`; the handler's first argument is a `CommandAuthenticatedInvocationContext` (`auth`, plus stage accessors). `anonymousAction()` receives a `CommandInvocationContext` parent. Both live in `src/core/commands/invocation-context.ts`. Only technical commands use `anonymousAction()`. On the context, `isAlphaEligible()` / `isBetaEligible()` answer whether **this execution** should be treated as alpha/beta — not merely whether `.stage()` names that lifecycle (see their own JSDoc in `invocation-context.ts` for the exact conditions). SonarCommand's own `lifecycle` getter is the stage snapshot used for tree visibility and help tags. Handlers record telemetry with `ctx.recordTelemetry(new TelemetryFact(name, payload))`. Facts live on that invocation context (`ctx.telemetryFacts()`), not a tree-owned buffer. `postAction` reads them from the action command's context, resolves the agent session id, then `commitTelemetryFacts` (`src/core/telemetry/index.ts`) emits handler facts concatenated with a `CliCommandExecuted` fact (`buildCommandExecutedFact` in `src/core/telemetry/command-executed.ts`; command/subcommand come from `SonarCommand.commandAndSubcommand()`) through generic `emitTelemetryEvent` and schedules the flush.
Mark lifecycle with `.stage(Stage.Stable)` (default), `.stage(Stage.Alpha)`, `.stage(Stage.Beta())` (Open Beta), `.stage(Stage.Beta('cli.beta.flag-key'))` (Private Beta, gated by LaunchDarkly), or `.stage(Stage.Deprecated({ sinceVersion, replacement }))`. Visibility is decided via `CliRuntime` (`isAlphaEnabled` from `SONARQUBE_CLI_ALPHA`, `isPrivateBetaEnabled` from LaunchDarkly). Deprecated commands stay visible and warn on every invocation (`replacement` is required; pass `null` when there is none). `createCommandTree` is async: it probes for Private Beta flag keys, then only when keys exist calls optional `loadPrivateBetaContext(flagKeys)` (wired in `src/index.ts` to resolve auth + `resolvePrivateBetaFlags`, 2-hour cache under `~/.sonar/sonarqube-cli/launch-darkly/`) and rebuilds the tree so Private Beta commands register only when the flag is `true`. With no keys (or no loader), LaunchDarkly is never contacted; docs call `await createCommandTree({ console })` without a loader so Private Beta stays omitted. Set `SONARQUBE_CLI_LAUNCHDARKLY_ENV=dev` to use the LaunchDarkly `dev` environment (default `production`). Open Beta and Deprecated appear in public docs; Private Beta and Alpha do not.
Contributors stage options with `addOption(new SonarOption('--flag', 'Help').stage(Stage.Alpha))`. Use `.stage(Stage.Beta())` for Open Beta, `.stage(Stage.Beta('cli.beta.flag-key'))` for Private Beta, and `.stage(Stage.Deprecated({ sinceVersion, replacement }))` for Deprecated. Docs include Open Beta and Deprecated options (with badges) and omit Alpha and Private Beta options. Invoking a deprecated command or passing a deprecated option prints a warning every time (`…is deprecated since <version> and will be removed in a future version.` then `Use '<command>' instead.` or `There is no replacement.`).
Visible top-level commands use their main `description()` as root help copy. Every visible top-level command should declare `rootHelp({ category })` so the custom root menu can group commands with blank lines between the `core`, `data`, `integrate`, and `cli-management` sections. The order within each group follows the declaration order in `src/commands/command-tree.ts`, so add or move top-level commands in the desired display order there. When a visible top-level command has visible subcommands, the custom root menu derives its label automatically as `name <sub1|sub2|...>` unless that command also sets `rootHelp({ expandSubcommands: true })`, in which case the parent command is rendered as just `name` and its visible subcommands are listed individually below it. Add `rootHelp({ label })` only when the default label is not enough. If a command should disappear from help entirely, declare it with Commander `{ hidden: true }` and leave an inline comment when hiding a public compatibility command.
The bare `sonar analyze` command accepts `-p, --project <project>` for the agentic portion of the combined flow. Use it to override auto-detection or to run `sonar analyze` without an installed project integration; `--branch` remains specific to `analyze agentic` / `verify`. SQAA accepts `--depth STANDARD|DEEP`: change-set and multi `--file` default to DEEP; single `--file` defaults to STANDARD unless `--depth DEEP` is set. Per-edit hooks force STANDARD; end-of-turn instructions tell agents to always pass `--depth DEEP` (even for a single file).

`sonar quality-gate status` shows the project-level quality gate verdict. Backed by `QualityGatesClient.getProjectStatus()` (
`src/core/server/quality-gates.ts`) calling `GET /api/qualitygates/project_status`, whose params and response shape are identical on SonarQube Cloud and Server (no `isCloud`
branching needed). `resolveQualityGateScope()` (`src/commands/quality-gate/status/scope.ts`) resolves the effective branch/PR: `--branch`/`--pull-request` win when given (mutually exclusive); otherwise it calls the shared `autoResolvePullRequest()` (`src/core/pull-request-auto-resolve.ts` — command-agnostic, so other commands with the same flags, e.g. `list issues`, can reuse it) to try to auto-detect a pull request for the current git branch via `PullRequestsClient.listPullRequests()` (`GET /api/project_pull_requests/list` — the project's own record of PRs it has analyzed, not a live DevOps-platform call, so no ALM credentials are needed; the endpoint carries no open/closed state, so a recently merged PR can still match while its branch survives locally), and falls back to the project's default branch whenever that lookup is unavailable, fails, empty, or ambiguous (no git branch resolvable, the lookup errors or 404s on an edition without PR analysis, or more than one PR matches). The output always states which branch/PR was actually used (`Branch main (default)` / `Pull Request 42 (auto-detected from branch feature-x)`), so the result is never ambiguous.

`sonar list issues --file <path>` scopes the search to one file or directory, resolved by `resolveFileComponentKey()` in `src/core/file-component.ts` (shared by any command taking `--file`) — see that file for the resolution mechanics. **Directory scope is intentionally non-recursive**: `GET /api/issues/search`'s `componentKeys` never recurses into subdirectories, verified live against a real project. Enumerating every file under a directory as a workaround was tried and rejected — a real, moderately-sized directory (201 files) already produces a query string the server rejects outright (`414 Request-URI Too Large`), and `issues/search` is GET-only, so there's no way around it. Documented, accepted limitation, not a bug to fix later.

`sonar list issues` defaults `--statuses` to `OPEN,CONFIRMED` (`DEFAULT_STATUSES` in `src/commands/list/issues.ts`) when the flag is omitted, so results are actionable issues by default rather than the full history including `FIXED`/`FALSE_POSITIVE`/`ACCEPTED`. Pass `--statuses` explicitly to see other states.

`sonar analyze dependency-risks` accepts an optional `-p, --project <project>`. When omitted, the project key is auto-detected via `discoverProject()`.

`sonar analyze dependency-risks` pre-scans discovered manifest files for secrets (via `sonar-secrets`) before the SCA scan and aborts if any are found. In the `analyze` path the secrets binary is a hard prerequisite (install failure aborts the run); in the git pre-commit hook path the manifest secrets _scan_ fails open on a scan error (skips/warns). See `dependency-risk-helpers/manifest-secrets-guard.ts`. This scan-error fail-open is distinct from the git/agent secrets-hook auth+binary gate: an unauthenticated user or a missing `sonar-secrets` binary blocks the commit/push (git hooks throw `MissingDependenciesError` → exit 1).

`sonar import` (hidden while in development) imports a repository from a connected DevOps platform into SonarQube by provisioning a bound project. The organization is always the one tied to the active connection (`auth.orgKey`), and the CLI verifies the caller is an admin of that org before proceeding. Only organizations bound to GitHub or Azure DevOps can be imported; `assertSupportedAlm()` rejects any other platform before repositories are listed. Accepts exactly one selection-mode flag: `--repo <slug>` (an explicit list — the flag equivalent of interactively choosing "Manual"), `--all` (every eligible repository — equivalent to "Recommended"), or `--regex <regex>` (only eligible repositories whose DevOps platform name, not slug, matches — equivalent to "By pattern"; accepts a `/pattern/flags` literal, e.g. `/^archived-/i`, for flags like case-insensitive matching, since JS has no inline `(?i)` modifier). These three are mutually exclusive; omitting all three interactively shows a Recommended/Manual/By pattern menu. `--non-interactive` requires one of the three. On success it prints the project list link (`{serverUrl}/organizations/{orgKey}/projects`) in the final outro. Implementation lives in `src/commands/import/`.

`sonar link <projectKey>` (barebones — UX will change) writes a single project binding to `.sonar-config.json` at the repository root via the shared `sharedProjectConfigRepository.set()` singleton (see "State and auth" in `.claude/rules/state-and-auth.md` for the file format), overwriting whatever `project` entry was already there. Supports one project per repository; monorepo support is not yet implemented. `<projectKey>` (SonarQube project key) is a positional argument; `--path <path>` (relative to the repo root, defaulting to `.`) is the only option — the server/org come from the active connection (`ctx.auth`), not from flags. `deriveEntryFromAuth()` branches on `auth.connectionType`: `on-premise` writes `serverUrl` as-is; `cloud` derives `region` via `cloudRegionFromUrl(auth.serverUrl)` and uses `auth.orgKey`, failing with `CommandFailedError` if either is unavailable (a Cloud connection with no org is already rejected earlier by `resolveAuth()` itself, so that half of the check is effectively unreachable in practice — the region half remains reachable, e.g. a non-standard Cloud host). `--path` is rejected as `--path must not be empty.` when blank (whitespace-only) — an empty `path` would write successfully but `load()` would then silently and permanently discard the entry via its own `isNonEmptyString` check. `--path` is also validated against the same containment rule `load()` enforces (`resolveContainedPath()`, see "State and auth"), failing with a `CommandFailedError` before writing when it is absolute or escapes the target directory, rather than silently writing an entry that a later `load()` would drop; this validation runs, and any failure is raised, before the no-git-repository warning below, so a rejected path never gets the misleading "Writing to the current directory instead." message. When run outside a git repository, it warns on stderr and writes `.sonar-config.json` to the current directory instead of failing. On success it prints the resolved project root, the project key, the config file's full path, and — only when a git repository was found, since there is nothing to commit otherwise — a hint to commit `.sonar-config.json` to share it. No merge, no removal. Implementation in `src/commands/link/index.ts`.

## System reset

`sonar system reset` returns the CLI to a factory-like state in one shot. Registered as `anonymousAction` so it works when auth is broken. Integration teardown is declarative-only: `integrations.installed` features are removed via `removeFeature()`; legacy `agentExtensions` entries are cleared from state in `clearLegacyState()` but are not used for on-disk cleanup (1.0 does not guarantee removal of pre-declarative artifacts). Binary cleanup removes `dependencies.installed` paths under `BIN_DIR`. `systemReset()` also unconditionally empties the persisted `state.knownServerProjectMappings` table — see "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why it needs this explicit reset. Partial reset (step warnings) exits `0`.

`sonar system status` displays a diagnostic overview: authentication (token verified live via `/api/authentication/validate`, four states: Not Set / Active / Invalid / Set Unverified), installed binaries with update availability, configured integrations with paths, and MCP Server configured/running status. Supports `--json` for machine consumption. Implementation in `src/commands/system/status.ts`. Token verification uses `checkTokenStatus` from `src/core/auth/token.ts`; CLI update availability comes from `Distribution/sonarqube-cli/stable.version`, while `sonar update` downloads the platform installer script from the GitHub `user-scripts/` directory when it actually performs the update. MCP config validation is JSON-based for Claude/Copilot (checks `mcpServers.sonarqube` structure) and trusts file existence for Codex TOML configs. A VORTEX section (`src/commands/system/status-vortex.ts`, resolved via `resolveVortexEntitlement` in `src/core/vortex/entitlement.ts`) is shown whenever Vortex is applicable — Cloud with an org, or Server where both the A3S and CAG hub queries answered (a 404 from either hub yields `not_applicable` and hides the section). It reuses `VortexEntitlementClient.hasVortexEntitlement()` (`enabled | over_consumption | not_entitled | check_failed | not_applicable`) rather than re-resolving independently. `src/core/vortex/entitlement.ts` is the single home for Vortex entitlement resolution, named after the domain (not any particular caller): a private `queryVortexEntitlement()` wraps the one client call, and `recheckVortexEntitlement()` (used to reinterpret a runtime 403) and `resolveVortexEntitlement()` (used by `system status`) both call through it rather than each constructing their own client; both return/consume `VortexEntitlementResult` (`src/core/vortex/entitlement.ts`) rather than a separate duplicate type. `not_applicable` covers unauthenticated and Cloud-without-org (decided before the API) plus a 404 from either Server hub (returned by `hasVortexEntitlement()` itself). It reports the combined status plus CAG usage (`consumed`/`limit`) only for `enabled`. Only genuine entitlement loss (`not_entitled`, when Vortex is actually applicable) flips the command unhealthy; quota exhaustion (`over_consumption`) and check failures stay healthy.

`sonar self-update` is a deprecated, hidden alias for `sonar update` (only when `CURRENT_DISTRIBUTION.enableSelfUpdate` is true; see `src/core/host/distribution.ts`), staged with `Stage.Deprecated({ sinceVersion: '1.4', replacement: 'sonar update' })`. Calling it prints a deprecation warning, then runs the same `updateVersion()` logic. Both are registered in `src/commands/command-tree.ts`.

`sonar verify` is a deprecated, hidden alias for `sonar analyze` / `analyze agentic`, staged with `Stage.Deprecated({ sinceVersion: '0.14', replacement: 'sonar analyze' })`.

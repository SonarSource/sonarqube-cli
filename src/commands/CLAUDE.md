# Commands

`sonar run mcp` reads `mcp.container.network`, `mcp.container.addHost`, `mcp.container.serverUrl`, and `mcp.container.autoNetwork` from persistent config on each launch for on-premise connections. The URL override affects only the MCP container, so host-side CLI commands keep the saved connection URL. Explicit settings (`network`/`addHost`/`serverUrl`) always take precedence. Automatic loopback handling is opt-in via `mcp.container.autoNetwork=true` (default `false`, so existing users see no behavior change until they set it): once enabled, a loopback URL with no explicit settings gets native Linux host networking, or a Docker/Podman host alias elsewhere. Generated agent MCP entries invoke `sonar run mcp`, so the same behavior applies to them. Agent integration and system status show loopback networking advice, including a nudge to set `mcp.container.autoNetwork` when it's off. A non-signal container failure writes a hint to stderr only when the container URL still uses loopback and networking advice is available. Shutdown exit codes 130 and 143 do not produce this hint. Cloud connections ignore these MCP networking settings.

The `hook/`, `context/` and `analyze/` handlers are the runtime half of the agent integrations that install them: `src/commands/integrate/CLAUDE.md` covers both halves and is the file to read before changing either.

`sonar auth login` selects the browser sign-in page in `src/core/auth/token.ts`. SonarQube Cloud uses `/auth`. SonarQube Server uses `/auth` from full-year version 2026.2, while Community Build uses it from short-year version 26.4. Earlier or unknown versions use `/sonarlint/auth`.

`sonar auth status` reports the active credentials and warns in text mode when a discovered project records a different connection that `sonar context` cannot use. Both commands compare the recorded server with `authMatchesRecordedServer()`: normalized server URLs must match for active-token use, and the organization is not compared. A different port is a different server even when the keychain account uses the same hostname. Cloud organization membership failures advise checking the token's account or asking an organization administrator to add the account. They do not depend on token age. Missing and unverified membership retain distinct JSON statuses and exit code 1.

`sonar auth org [org]` switches the stored SonarQube Cloud login to another organization without a new login. It fails on SonarQube Server, and when environment variable authentication is active, because the variables override the stored login. With a key, it checks that the token is a member of the organization. Without one, it shows the same picker as `sonar auth login`. It rewrites only the recorded connection and keeps its token name, so `sonar auth logout` can still revoke the token. The keychain entry is keyed by the server hostname, so the token stays as it is. Integrations installed by `sonar integrate` keep the old organization. Implementation in `src/commands/auth/org.ts`.

To add a new command: implement the logic in a new folder under `src/commands/` and register it in `createCommandTree()` in `src/commands/command-tree.ts`, or in the command module that `createCommandTree()` delegates to (for example, `architecture/register.ts`).
Please declare commands using the type defined in `src/core/commands/sonar-command.ts`.
Lifecycle stages (`Stage`) live in `src/core/commands/stage.ts` and are re-exported from `sonar-command.ts`. Qualified invocation paths used in lifecycle warnings live in `src/core/commands/path.ts`.
By default, new commands should register a `authenticatedAction()`; the handler's first argument is a `CommandAuthenticatedInvocationContext` (`auth`, a memoised `connection`, plus stage accessors). `anonymousAction()` receives a `CommandInvocationContext` parent. Both live in `src/core/commands/invocation-context.ts`. Only technical commands use `anonymousAction()`. Handlers resolve credentials through `ctx.resolveAuth()` — memoized on `CliRuntime`'s `AuthResolver`; authenticated handlers also expose `ctx.auth`. Hooks and status paths that must degrade gracefully use `ctx.resolveAuthOrNull()`, or `ctx.resolveConnection()` when they also need a transport: it returns a `SonarConnection` (`auth` plus the `SonarHttpClient` bound to its server, `src/core/server/connection.ts`) or `null` when there are no usable credentials, which is what `ctx.connection` exposes synchronously on the authenticated context. Private Beta entitlement uses `runtime.flagsResolver`. On the context, `isAlphaEligible()` / `isBetaEligible()` answer whether **this execution** should be treated as alpha/beta — not merely whether `.stage()` names that lifecycle (see their own JSDoc in `invocation-context.ts` for the exact conditions). SonarCommand's own `lifecycle` getter is the stage snapshot used for tree visibility and help tags. Handlers record telemetry with `ctx.recordTelemetry(new TelemetryFact(name, payload))`. Facts live on that invocation context (`ctx.telemetryFacts()`), not a tree-owned buffer. `postAction` reads them from the action command's context, resolves the agent session id, then `commitTelemetryFacts` (`src/core/telemetry/index.ts`) emits handler facts concatenated with a `CliCommandExecuted` fact (`buildCommandExecutedFact` in `src/core/telemetry/command-executed.ts`; command/subcommand come from `SonarCommand.commandAndSubcommand()`, `arguments` from `SonarCommand.describeInvocationArguments()`) through generic `emitTelemetryEvent` and schedules the flush. Two root `preAction` hooks run before any handler, in order: Sentry init, then `runPostUpdateActions`.
Each command decides for itself whether it may prompt. `Console` prompts do not check for a terminal, and they wait forever when stdin is piped or closed. Gate every prompt with `console.canPrompt()` (stdin is a terminal, or `SONARQUBE_CLI_MOCK_TTY` is set; see `confirmSignInWithDifferentAccount` in `src/commands/auth/login.ts` and `src/commands/config/set.ts`). It only reports; it never gates a prompt itself. `FakeConsole` defaults it to `true`; use `setCanPrompt(false)` in unit tests instead of patching `process.stdin.isTTY`, and make the non-interactive path fail or continue with a message that does not rely on the prompt. Integration tests set `SONARQUBE_CLI_MOCK_TTY=1` to reach the prompt through `harness.runInteractive()`. They do not run the CLI on a real pty.
Mark lifecycle with `.stage(Stage.Stable)` (default), `.stage(Stage.Alpha)`, `.stage(Stage.Beta())` (Open Beta), `.stage(Stage.Beta('cli.beta.flag-key'))` (Private Beta, gated by LaunchDarkly), or `.stage(Stage.Deprecated({ sinceVersion, replacement }))`. Visibility is decided via `CliRuntime` (`isAlphaEnabled` from `SONARQUBE_CLI_ALPHA`, `isPrivateBetaEnabled` from LaunchDarkly). Deprecated commands stay visible and warn on every invocation (`replacement` is required; pass `null` when there is none).
`createCommandTree` builds the tree once (recording Private Beta flag keys as staged commands/options register). Before `parseAsync`, `src/index.ts` calls `runtime.flagsResolver.resolveFlags()` then `refreshStagedVisibility()`. Docs generation calls `createCommandTree({ console })` without resolving flags, so Private Beta stays omitted. Set `SONARQUBE_CLI_LAUNCHDARKLY_ENV=dev` to use the LaunchDarkly `dev` environment (default `production`). Open Beta and Deprecated appear in public docs; Private Beta and Alpha do not.
Contributors stage options with `addOption(new SonarOption('--flag', 'Help').stage(Stage.Alpha))`. Use `.stage(Stage.Beta())` for Open Beta, `.stage(Stage.Beta('cli.beta.flag-key'))` for Private Beta, and `.stage(Stage.Deprecated({ sinceVersion, replacement }))` for Deprecated. Docs include Open Beta and Deprecated options (with badges) and omit Alpha and Private Beta options. Invoking a deprecated command or passing a deprecated option prints a warning every time (`…is deprecated since <version> and will be removed in a future version.` then `Use '<command>' instead.` or `There is no replacement.`).
Visible top-level commands use their main `description()` as root help copy. Every visible top-level command should declare `rootHelp({ category })` so the custom root menu can group commands with blank lines between the `core`, `data`, `integrate`, and `cli-management` sections. The order within each group follows the declaration order in `src/commands/command-tree.ts`, so add or move top-level commands in the desired display order there. When a visible top-level command has visible subcommands, the custom root menu derives its label automatically as `name <sub1|sub2|...>` unless that command also sets `rootHelp({ expandSubcommands: true })`, in which case the parent command is rendered as just `name` and its visible subcommands are listed individually below it. Add `rootHelp({ label })` only when the default label is not enough. If a command should disappear from help entirely, declare it with Commander `{ hidden: true }` and leave an inline comment when hiding a public compatibility command.
The bare `sonar analyze` command accepts `-p, --project <project>` for the agentic portion of the combined flow. Use it to override auto-detection or to run `sonar analyze` without an installed project integration; `--branch` remains specific to `analyze agentic` / `verify`. SQAA accepts `--depth STANDARD|DEEP`: change-set and multi `--file` default to DEEP; single `--file` defaults to STANDARD unless `--depth DEEP` is set. Per-edit hooks force STANDARD; end-of-turn instructions tell agents to always pass `--depth DEEP` (even for a single file).

SQAA (A3S) matches each `files[].path` against the project's original analysis root and never recomputes it, so every SQAA entry point (`analyze agentic`, bare `sonar analyze`, the per-edit hooks) sends paths relative to the root of the project that owns the file, as `SqaaPath.serverPath` (`resolveSqaaPath` in `analyze/sqaa-paths.ts`). Displayed paths keep their own base, `SqaaPath.displayPath`: cwd for `--file`, the repository root for the change set. Issues echoed back under the server path are rewritten to the display path. Project discovery starts from cwd.

In a monorepo one run can span several projects. `resolveSqaaConnectionAndProject()` (`analyze/sqaa-resolution.ts`) takes the run's files and returns them split into `SqaaProjectGroup`s (`{ projectKey, projectRoot, files }`) via `DiscoveredProjects.groupByMapping()`: each file goes to the mapping with the deepest root containing it (see `state-and-auth.md`), plus the `ignored` files no project of the active connection owns, as `IgnoredFile`s: `outside-project` for files owned by no mapping, `other-connection` for files owned by a mapping recorded against another server or organization (`authMatchesRecordedConnection()`: normalized URL, and on Cloud the organization too). Source only ever goes through the active connection, so those groups are never uploaded; change-set files are reported as ignored with that reason (`excludeIgnoredFiles()`), and explicit `--file` arguments among them are an input error (`assertExplicitFilesAnalyzable()`, other-connection first). Filtering happens after nearest-wins grouping, so a nested other-connection project's files are not handed to the project above it. Grouping runs over `DiscoveredProjects.focusedOn(cwd)`, not every discovered mapping: run from inside a project (its root or any subdirectory) and only that closest project is analyzed, so the other projects' change-set files come back ignored as `outside-project`; run from above several projects (the monorepo root) and all of them are, as are projects nested inside the cwd project. Before running, `resolveSqaaRunFiles()` (`analyze/sqaa-paths.ts`) turns the groups into `SqaaRunFiles`: `projects` (`{ projectKey, files: SqaaPath[] }`, each file carrying its absolute, server and display path) plus the `displayProjects` / `displayPaths` views derived from them, so no caller remaps them. Every analysis then loops the projects (`runSqaaGroups()` in `analyze/sqaa-run.ts`): one `runAnalyses()` and one `SqaaProgress` per project (when the run spans more than one, its live display gains a `Project i/N · key` line above `Analyzing N files…`), tallies merged by `mergeTallies()`, results in group order (the order each project's first file appeared in). A global error (auth, entitlement) is organization-wide, so it stops the remaining projects. The report is grouped by project for display only: the text report puts each project under a `key · N files · M issues` header (`SqaaDisplayProject`, `printSqaaTextReport`'s `projects` option), but only when the run spans more than one project, so single-project runs render as before. Ignored files belong to no project, so in a grouped report they get their own `Not analyzed · N files` section after the last project (in JSON they were already the separate `ignored[]`). The JSON report stays flat and run-wide (`files[]`, `failures[]`, `summary`) and gains an optional `project` (key) on each `files[]` and `failures[]` entry, set for every grouped run (even one project) so consumers can group with a single `groupBy`; it is deliberately not nested, since the hook formatter, the combined `sonar analyze --format json` report and external parsers read the flat arrays. The single `CliAnalysisCompleted` event stays per run, not per project. `project_uuid` is noted only when the run involves exactly one project key, since it holds a single value (the telemetry shape for multi-project runs is an open question in MMF-5785's refinement).

An explicit `--project` pins every file to that key. Its root is the root of the discovered mapping with that key, falling back to the repository root (cwd outside git) when discovery has none; files outside that root are ignored as `outside-project`. Discovery for an explicit `--project` skips the git-remote lookup (`useGitRemoteBinding: false`), since only the root is needed from it. `outside-project` change-set files are reported as ignored; explicit `--file` arguments owned by no project are an input error naming every root they were matched against (`assertInsideProjectRoots()`, reached through `assertExplicitFilesAnalyzable()`). When discovery finds nothing at all for the directory, resolution is still `no-project`, so `requireProject` and the bare-`analyze` skip behave as before. The per-edit single-file hooks (Claude, Devin via `handleSqaaPostToolUse` in `hook/agent-post-tool-use.ts`; OpenCode and Pi via `createPostToolUseHook`) resolve the edited file's project with `resolveHookProject()` (`hook/sqaa-hook-project.ts`): `discoverSqaaProjects()`, then `focusedOn(cwd).groupByMapping([file])`, so in a monorepo each edit is analyzed under the project whose root is deepest around it, with its path relative to that root, and an edit no project owns is skipped silently. A project recorded against another server or organization is skipped too (`authMatchesRecordedConnection()`), as in `sonar analyze`, and the nearest owner wins, so its file never falls to a project above it. This replaced `discoverProject()`, which treated several projects under the cwd as ambiguous and resolved nothing. The Codex hook (`hook/codex-post-tool-use.ts`) analyzes the whole change set, so it passes no `project` to `buildSqaaJsonReport` and lets `resolveSqaaConnectionAndProject()` group it like `sonar analyze`; it sets `silentSkip` (`AnalyzeSqaaRunOptions`), which makes a missing project or organization skip without the console warning, since a global integration runs the hook in every repository. Files owned by no project, or by one recorded against another connection, come back in the report's `ignored[]`.

`sonar quality-gate status`: `src/commands/quality-gate/CLAUDE.md` covers the project-level verdict, branch/PR resolution, and file/directory scoping.

`sonar system status` checks the Docker, Podman, or nerdctl runtime only when an installed MCP integration has a valid configuration. It reports the shared runtime once as ready, not ready, or not found in text and as top-level `mcpRuntime` in JSON. On Windows, the bounded health probe follows the `SONARQUBE_CLI_MCP_WSL` policy used by `sonar run mcp`: `auto` tries WSL only when every native runtime executable is missing, `always` checks WSL only, and `never` checks native runtimes only. The status recommendation and integration warning use the same runtime message, including timeout and WSL context. It does not start the MCP server.

`sonar list issues`, `sonar remediate`, and `sonar analyze dependency-risks` share the Cloud project preflight in `src/core/project-organization.ts`. After resolving and noting the project, they look up the root component before issue searches, remediation entitlement checks or submissions, or SCA orchestration. The project must belong to the active organization; mismatched or missing/inaccessible projects raise `ProjectOrganizationError` (`src/core/errors.ts`), with CLI recovery hints supplied by `remediationHintFor()` in `src/core/commands/command-error.ts`. Other lookup failures propagate. Server connections skip this check.

`sonar list issues --file <path>` scopes the search to one file or directory, resolved by `resolveFileComponentKey()` in `src/core/file-component.ts` (shared by any command taking `--file`) — see that file for the resolution mechanics. **Directory scope is intentionally non-recursive**: `GET /api/issues/search`'s `componentKeys` never recurses into subdirectories, verified live against a real project. Enumerating every file under a directory as a workaround was tried and rejected — a real, moderately-sized directory (201 files) already produces a query string the server rejects outright (`414 Request-URI Too Large`), and `issues/search` is GET-only, so there's no way around it. Documented, accepted limitation, not a bug to fix later.

`sonar list issues` defaults `--statuses` to `OPEN,CONFIRMED` (`DEFAULT_STATUSES` in `src/commands/list/issues.ts`) when the flag is omitted, so results are actionable issues by default rather than the full history including `FIXED`/`FALSE_POSITIVE`/`ACCEPTED`. Pass `--statuses` explicitly to see other states. `-p, --project <project>` is optional: when omitted, the project key is auto-resolved via `resolveProjectKey()`/`discoverProject()` (see "known-server-project-mappings" in `.claude/rules/state-and-auth.md`), same mechanism as `sonar quality-gate status`. `--branch`/`--pull-request` are mutually exclusive; when neither is given, the shared `autoResolvePullRequest()` (`src/core/pull-request-auto-resolve.ts`) tries to match a pull request to the current git branch, printing `Using pull request <id> (auto-detected from branch <branch>)` on a hit. Unlike `quality-gate status`, there's no default-branch fallback: no match leaves both unset and `GET /api/issues/search` applies its own default silently.

`sonar list issues --new-code` limits results to issues found in the new code period (the "leak period"). It shares its Cloud/Server wire-param split with `quality-gate status`'s issue/security breakdowns, which instead derive the value per condition rather than from a direct flag.

`sonar list orgs` (alias `sonar list org`) lists the SonarQube Cloud organizations the authenticated user has access to, via `OrganizationsClient.listUserOrganizations()`; it fails on a Server connection. It supports `--page`/`--page-size` and `--format json|table` like `list projects`, but defaults to `table`. JSON exposes `isAdmin`/`isActive` as separate booleans, built by `toOrganizationSummary()` in `src/core/domain/organization.ts`; the table collapses both into one unlabeled NAME/KEY/status column (`active`, `Admin` or `Member`, active organization first) via `formatOrganizationRows()` in `src/commands/components/organization/rows.ts`. The `sonar auth login` organization picker renders its options with the same function, so the two displays stay identical. The picker and the key validation and prompt flow behind it live in `src/commands/components/organization/select.ts`, shared with `sonar auth org`. The caller passes the active organization key (`login` and `auth org` pass the resolved auth's `orgKey`), so that module reads no state.

`sonar analyze dependency-risks` accepts an optional `-p, --project <project>`. When omitted, the project is the single one `discoverProjects()` + `scope(cwd)` finds (`dependency-risk-helpers/sca-scan-target.ts`). In a monorepo linked with `.sonar-config.json` (CLI-1271), a directory covering several projects, or none of the linked ones, fails with the same `unresolvedProjectError()` as the `sonar context` passthrough (`src/core/project-discovery/unresolved-project.ts`). The scan runs from the project root, not cwd: an explicit `-p` uses the root of the linked project with that key, so `-p <key>` works from the repository root, and falls back to cwd when no linked project has that key.

`sonar analyze dependency-risks` pre-scans discovered manifest files for secrets (via `sonar-secrets`) before the SCA scan and aborts if any are found. In the `analyze` path the secrets binary is a hard prerequisite (install failure aborts the run); in the git pre-commit hook path the manifest secrets _scan_ fails open on a scan error (skips/warns). See `dependency-risk-helpers/manifest-secrets-guard.ts`. This scan-error fail-open is distinct from the git/agent secrets-hook auth+binary gate: an unauthenticated user or a missing `sonar-secrets` binary blocks the commit/push (git hooks throw `MissingDependenciesError` → exit 1).

`sonar import` imports a repository from a connected DevOps platform into SonarQube by provisioning a bound project. The organization is always the one tied to the active connection (`auth.orgKey`), and the CLI verifies the caller is an admin of that org before proceeding. Accepts exactly one selection-mode flag: `--repo <slug>` (an explicit list — the flag equivalent of interactively choosing "Manual"), `--all` (every eligible repository — equivalent to "Recommended"), or `--regex <regex>` (only eligible repositories whose DevOps platform name, not slug, matches — equivalent to "By pattern"; accepts a `/pattern/flags` literal, e.g. `/^archived-/i`, for flags like case-insensitive matching, since JS has no inline `(?i)` modifier). These three are mutually exclusive; omitting all three interactively shows a Recommended/Manual/By pattern menu. `--non-interactive` requires one of the three. On success it prints the project list link (`{serverUrl}/organizations/{orgKey}/projects`) in the final outro. Implementation lives in `src/commands/import/`. On SonarQube Server it first refuses a server older than 2025.1 (the previous LTA; an unreadable version is let through). The repositories come from a DevOps platform setting (`--dop-setting <key>`, or chosen interactively when several exist): the CLI never handles the caller's personal access token, so when it is missing or rejected it prints the web UI link (`{serverUrl}/projects/create?mode=<platform>`) and, when it can prompt, opens it and waits until the token is connected; `ServerBackend` then lists the platform's repositories and imports each one with `PUT /api/v2/dop-translation/bound-projects`.

`sonar link <projectKey>` (barebones — UX will change) writes a single project binding to `.sonar-config.json` at the repository root via the shared `sharedProjectConfigRepository.set()` singleton (see "State and auth" in `.claude/rules/state-and-auth.md` for the file format), overwriting whatever `project` entry was already there. `.sonar-config.json` itself can express several projects (a `projects` array, for a monorepo — see `discoverProjects()` in "State and auth"), but plain `sonar link` never writes one: it always writes the legacy singular `project` key, so a `projects` array already in the file is left untouched (and effectively shadows the `project` entry it just wrote, since `discoverProjects()` prefers `projects` when both are present); `set()` reports this and plain `sonar link` then warns that the link is ignored, pointing to `sonar link --monorepo`. `sonar link --monorepo <projectKey> [--path <path>]` is the multi-project counterpart: same arguments, validation and output, selected by the `--monorepo` flag (not a subcommand), but it writes through `sharedProjectConfigRepository.addProject()`, which creates the `projects` array if needed, appends the entry, and updates the existing entry in place when its canonical directory is already mapped (so `services/api`, `./services/api/` and `services/web/../api` do not duplicate). `addProject()` stores paths relative to the config directory with forward slashes, preserves other root fields and a legacy singular `project` (which `projects` then shadows), and refuses to write when the file is unparseable, not an object, or has a non-array `projects`. `<projectKey>` (SonarQube project key) is a positional argument; `--path <path>` (relative to the repo root, defaulting to `.`) and `--monorepo` are the only options — the server/org come from the active connection (`ctx.auth`), not from flags. `deriveEntry()` branches on `auth.connectionType`: `on-premise` writes `serverUrl` as-is; `cloud` writes `region` and `organization` for URLs with a production Cloud origin, including URLs with a trailing slash or different casing. It writes `serverUrl` and `organization` for any other Cloud URL, including staging, so the shared config retains the actual host. A missing organization fails with `CommandFailedError`. `--path` is rejected as `--path must not be empty.` when blank (whitespace-only) — an empty `path` would write successfully but `load()` would then silently and permanently discard the entry via its own `isNonEmptyString` check. `--path` is also validated against the same containment rule `load()` enforces (`resolveContainedPath()`, see "State and auth" in `.claude/rules/state-and-auth.md`), failing with a `CommandFailedError` before writing when it is absolute or escapes the target directory, rather than silently writing an entry that a later `load()` would drop; this validation runs, and any failure is raised, before the no-git-repository warning below, so a rejected path never gets the misleading "Writing to the current directory instead." message. When run outside a git repository, it warns on stderr and writes `.sonar-config.json` to the current directory instead of failing. On success it prints the resolved project root, the project key, the config file's full path, and — only when a git repository was found, since there is nothing to commit otherwise — a hint to commit `.sonar-config.json` to share it. No removal. Implementation in `src/commands/link/`.

`sonar link list [--path <path>] [--pattern <regex>] [--page N] [--page-size N]` (`link/list-links.ts`, CLI-1338) is the read-only JSON lookup for monorepos, so an agent never needs the full directory→project mapping, which at real customer scale (tens of thousands of projects) would not fit a context window. `--path` is any existing file or directory (default cwd; a file starts discovery from its directory). It runs `discoverProjects()` from there and lists only the projects at, under or enclosing that path (`scope()`), ordered by directory hops from it, each with `contains` (its root contains the path, as tagged by `scope()`), optionally filtered by a case-insensitive regex on the project key or its directory relative to the repository root, or to the current directory outside a git repository so the base never moves with `--path` (never the absolute path, whose checkout prefix would match everything), paginated with `{ projects, paging }` like `list projects` (default page size 20, mirroring CAG's "--limit 20 or less" convention; max 100). The help deliberately makes no claim about which project `sonar context` would use: for a directory without `--pattern`, a `paging.total` of 1 is that project (even with `contains: false`, since `scope()` also matches projects below), but for a file it may not be, because `sonar context` resolves by directory and the file's directory can also hold a nested project; several with `contains: true` are nested projects, which `sonar context` cannot resolve yet. It is authenticated so git-remote binding resolves the same way it does for `sonar context`. Commander dispatches `list` as a subcommand, so a project literally keyed `list` cannot be linked by the positional.

`sonar stats` (CLI-1113, Alpha) reads the local ledger built by `src/core/stats/` (see that directory's `CLAUDE.md`) and renders the text card or `--json` shape defined in MMF-5834. `--since 7d|14d|30d|all` (default `30d`); the all-time column and `agentBreakdown`/`firstSeenMs` always come from `stats_aggregates`, purge-safe by design. `agentHitRate` is windowed (from surviving `stats_events` rows) except at `--since all`, where it also reads `stats_aggregates`. At `--since all` the windowed breakdowns (`analyzers`/`triggers`/`callerCommandBreakdown`/`topRules`/`topSecretTypes`) also read from `stats_aggregates` instead of `stats_events`, since raw rows past the 1-year retention are gone — `stopped` (secrets-blocked-by-point) is the one exception, with no aggregate dimension of its own, so it can under-count `allTime.secretsBlockedTotal` once old rows are purged (CLI-1115). Query layer: `src/core/stats/stats-queries.ts`/`stats-aggregation.ts`; rendering (sparklines, bars, entitlement placeholders): `src/commands/stats/text-report.ts`.

`sonar architecture` (alias `arch`, stable) reads the public `current-architectures` and `intended-architectures` APIs only. There is no endpoint selector or private fallback. Current reads support component/depth/language drilldown with text, TOON or JSON output, capped across languages at 150 nodes, 20 dependencies and 5 feedback pairs; public graphs have no graphId. Intended reads return revision and models; component/depth views are partial and cannot be written back. Language-filtered CLI exports retain a CLI-only language scope and cannot be passed to MCP architecture_set; use an unfiltered export to move a model between CLI and MCP. Project discovery uses the existing shared resolver with the authenticated connection, including its normal local configuration and git-remote binding fallbacks. Unresolved projects need --project. Architecture commands omit private project identity telemetry enrichment. Cloud uses public organization and main-branch lookups. Server current reads use the fixed organization UUID; Server intended commands fail clearly until a confirmed public project UUID lookup exists.

`intended set --file <file> [--dry-run]` validates complete public exports, checks the semantic revision and model UUID before changing an existing model, and saves an owner-only backup. Creation uses public POST with `{projectId, intendedArchitectures}`; updates use public PATCH by model UUID with `application/merge-patch+json` and the complete perspectives array. The response root id identifies the model; all perspectives use public qualifiers on the wire, mapped to CLI type. Current queries use language. Language-scoped CLI files preserve other languages. Explicit clear (`models: []`, or removal of the last scoped language) uses DELETE only, because PATCH with an empty array would leave a model invisible to the public export. Failed writes re-read public state: verified desired content counts as success; any other or unknown state stops with backup instructions. No automatic rollback or DELETE/POST replacement is attempted. The API has no conditional revision support, so changes after preflight cannot be ruled out. Public perspective labels/descriptions and group descriptions/patternId import links round-trip; the server resolves linked groups and ignores submitted expanded children. Unknown fields are omitted; pattern strings retain backend semantics. Server ids stay internal and do not affect revisions. Windows backups inherit user directory ACLs; POSIX backups and directories are owner-only. SonarQube applies changes from the next analysis.

## Architecture directives

`architecture directives get` reads one public page (`--page`, `--page-size`), or one directive with `--id`. `architecture directives set --file <file> [--dry-run]` accepts `{create: [...], update: [{id, changed fields}], delete: [{id}]}`. Lists are optional; unspecified update fields and unmentioned directives are retained. Both commands use standard authentication and project discovery. Preflight the whole batch and reject conflicting IDs before writing. Create duplicate checks read every page, normalize absent perspectives to `default_perspective`, and reject batches exceeding 1000 stored directives before writes. Creations record `sonarqube-cli` as their origin. Updates send required structural fields and explicitly supplied optional fields, retaining the origin from a fresh project-validated read. New or identity-changing directives warn about missing exact keys in the complete current graph; unavailable or unsupported views produce a warning, without blocking writes. Description-only changes and deletions do not fetch graphs. Concurrent changes can still race these reads. Writes are individual, without automatic retry or rollback; partial failures report confirmed IDs. Directives are Cloud-only until public project UUID resolution is available on Server. Optional fields cannot be cleared with null; the API has no conditional writes.

## Run MCP

`sonar run mcp` accepts `SONARQUBE_CLI_MCP_WSL=auto|always|never` on Windows. `auto` checks native Docker, Podman, and Nerdctl first. It checks WSL only when all native executables are missing. A native `info` failure blocks WSL fallback and produces a runtime-specific error. `always` checks WSL only. `never` checks native runtimes only. Values are case-insensitive and trimmed; blank values use `auto`. The variable is ignored on other platforms. Native failure messages show up to three lines and 1000 characters of diagnostic output and explain how to select WSL. A failed `always` search reports that only WSL was checked. Runtime selection is in `src/core/host/environment/tool-detector.ts`; startup errors are in `src/commands/run/mcp.ts`.

## System reset

`sonar system reset` returns the CLI to a factory-like state in one shot. Registered as `anonymousAction` so it works when auth is broken. Integration teardown is declarative-only: `integrations.installed` features are removed via `removeFeature()`; legacy `agentExtensions` entries are cleared from state in `clearLegacyState()` but are not used for on-disk cleanup (1.0 does not guarantee removal of pre-declarative artifacts). Binary cleanup removes `dependencies.installed` paths under `BIN_DIR`. `systemReset()` also unconditionally empties the persisted `state.knownServerProjectMappings` table — see "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why it needs this explicit reset. The local `sonar stats` SQLite ledger (see `src/core/stats/CLAUDE.md`) is wiped outright, as its own reported step (`clearStats()`, `src/commands/system/reset-stats.ts`) rather than folded into the generic filesystem-cache step, per the CLI-1114 ADR. `sonar config` configuration is preserved by default; `--all` removes it as its own step (`clearConfig()`, `src/commands/system/reset-config.ts`): the whole `cli-config.properties` file plus every sensitive key's `config/<key>` keychain entry. Partial reset (step warnings) exits `0`.

`sonar system status` displays a diagnostic overview: authentication (token verified live via `/api/authentication/validate`, four states: Not Set / Active / Invalid / Set Unverified), installed binaries with update availability, configured integrations with paths, and MCP Server configured/running status. Supports `--json` for machine consumption. Implementation in `src/commands/system/status.ts`. Token verification uses `checkTokenStatus` from `src/core/auth/token.ts`; CLI update availability comes from `Distribution/sonarqube-cli/stable.version`, while `sonar update` downloads the platform installer script from the GitHub `user-scripts/` directory when it actually performs the update. MCP config validation is JSON-based for Claude/Copilot (checks `mcpServers.sonarqube` structure) and trusts file existence for Codex TOML configs. A VORTEX section (`src/commands/system/status-vortex.ts`, resolved via `resolveVortexEntitlement` in `src/core/vortex/entitlement.ts`) is shown whenever Vortex is applicable — Cloud with an org, or Server where both the A3S and CAG hub queries answered (a 404 from either hub yields `not_applicable` and hides the section). It reuses `VortexEntitlementClient.hasVortexEntitlement()` (`enabled | over_consumption | not_entitled | check_failed | not_applicable`) rather than re-resolving independently. `src/core/vortex/entitlement.ts` is the single home for Vortex entitlement resolution, named after the domain (not any particular caller): a private `queryVortexEntitlement()` wraps the one client call, and `recheckVortexEntitlement()` (used to reinterpret a runtime 403) and `resolveVortexEntitlement()` (used by `system status`) both call through it; both take the caller's `SonarConnection` as their only parameter instead of building a transport or re-resolving auth, and both return/consume `VortexEntitlementResult` (`src/core/vortex/entitlement.ts`) rather than a separate duplicate type. `not_applicable` covers Cloud-without-org (decided before the API) plus a 404 from either Server hub (returned by `hasVortexEntitlement()` itself). It reports the combined status plus CAG usage (`consumed`/`limit`) only for `enabled`. Only genuine entitlement loss (`not_entitled`, when Vortex is actually applicable) flips the command unhealthy; quota exhaustion (`over_consumption`) and check failures stay healthy.

The MCP runtime health check uses the launcher's Docker, Podman, then nerdctl order. It stops when a probe times out and reports that runtime as not responding. The MCP launcher keeps its untimed probe.

`sonar self-update` is a deprecated, hidden alias for `sonar update` (only when `CURRENT_DISTRIBUTION.enableSelfUpdate` is true; see `src/core/host/distribution.ts`), staged with `Stage.Deprecated({ sinceVersion: '1.4', replacement: 'sonar update' })`. Calling it prints a deprecation warning, then runs the same `updateVersion()` logic. Both are registered in `src/commands/command-tree.ts`.

`sonar update` runs the standalone installer only when `process.execPath` matches that installer's per-user destination: `$HOME/.local/share/sonarqube-cli/bin/sonar` on Unix or `%LOCALAPPDATA%\sonarqube-cli\bin\sonar.exe` on Windows. Other installation paths fail before the version check, including with `--force`. `update status` and the deprecated `--status` flag remain read-only and available from any path. The build distribution marker alone does not identify how a binary was installed.

When an update is available, `update status` and `sonar system status` recommend `sonar update` only for a CLI at the standalone installer path. Other installations show guidance to use their organization, package manager, or original installation method.

The location check resolves symlinks on the running executable and the installer directory, including symlinked parent directories. It does not follow a symlink at the expected executable leaf, so a link from the installer path to an externally managed binary stays ineligible.

When `sonar update` runs from source through Bun, it explains that only an installed CLI can update itself. An unset or different home directory still fails the location check with the generic external-installation guidance.

`sonar verify` is a deprecated, hidden alias for `sonar analyze` / `analyze agentic`, staged with `Stage.Deprecated({ sinceVersion: '0.14', replacement: 'sonar analyze' })`.

`sonar update` detects the Homebrew cask when the canonical executable path contains `/Caskroom/sonarqube-cli/` under any prefix, including through a `bin/sonar` symlink. It exits with code 1 before checking or installing updates, including with `--force`. It recommends `brew upgrade --cask sonarqube-cli`. The remediation hint explains why the CLI does not run Homebrew. Read-only update status, system status recommendations, and post-command update notices also recommend `brew upgrade --cask sonarqube-cli` for this cask. Standalone updates keep their existing behavior.

`sonar api` prints successful response bodies to stdout. Non-2xx responses exit with code 1 and print `SonarQube API error: <status> <status text> - <response body>` to stderr. The body is unparsed; an empty body omits the separator. This handling is specific to `SonarHttpClient.genericRequest`; domain clients retain status-specific error parsing. Generic requests retain rate-limit and service-unavailable retry hints and critical server-error classification.

# Commands

`sonar onboard [--project-key <key>] [--format text|json] [--verbose]` creates a **new private unbound project**, reuses a compatible SonarScanner CLI on PATH or the managed cache, installing the pinned archive with its embedded JRE only when neither is available, submits a full analysis, waits up to 600 seconds for that exact compute-engine task, and prints its quality gate, dashboard URL, and the first 20 active issues using the shared `list issues` API client and table renderer. Authentication supplies the server and Cloud organization (required on Cloud). Without `--project-key`, local project configuration is checked first via `discoverProject({ auth: null, useKnownMappings: false })`. If no key is detected, `project-key.ts` generates one deterministically as `<organization_><normalized-name>-<12-character SHA-256 suffix>` (organization prefix only when present). Git origin supplies the name and credential-free host/repository identity; HTTPS, SCP-style SSH, and SSH URLs for the same repository produce the same key. Without a usable origin, the main Git working tree folder name is used, or the current folder name outside Git. The hash includes the organization and identity, distinguishes names that normalize identically, and excludes local checkout paths for named directories and network origins. Generated Git targets scan the current repository root; generation does not prompt or write a binding. An explicit key uses the invocation directory; a detected key uses its discovered project root and must match the active connection. Existing keys fail without scanning or creating bindings. Maven, Gradle, and .NET build markers fail early with dedicated-scanner guidance. No `.sonar-config.json`, scanner properties, or DevOps binding is written. Scanner work, task metadata, and converted TLS stores live in a temporary directory and are removed after the run. Failed analyses retain the created project and scanner installation; a failed quality gate is reported without failing onboarding itself.

Onboarding output defaults to `text` for all callers; agents select `--format json` explicitly, following the existing command pattern. JSON stdout is one document containing `projectKey`, `projectName`, `analysis`, `qualityGate`, `dashboardUrl`, `issues`, `paging`, `scannerLogPath`, `scannerOutput`, `messages`, and `warnings`. Text normally displays a spinner during scanning and omits scanner logs before the final issue table. `--verbose` streams redacted scanner logs as lines arrive and suppresses that spinner. In JSON mode verbose logs stream to stderr to keep stdout parseable, and `scannerOutput` is included in the JSON only when verbose is requested. Progress and warnings remain in the JSON document; it uses the existing explicit-format startup buffering. Text output labels the gate, shows the full-results link, wraps issues to the terminal width, and supplies a next-page `sonar list issues` command when needed. Issues are scoped to the newly scanned project/default branch with OPEN/CONFIRMED statuses, without Git pull-request auto-detection. Issue/gate retrieval failures preserve completed analysis, report warnings, and use null fields rather than claiming zero issues. Scanner stdout/stderr is always saved as it arrives to a private, token-redacted `logs/sonar-scanner-<uuid>.log`; failures include its path.

Implementation is in `src/commands/onboard/`. The scanner installer is `src/core/host/install/sonar-scanner.ts`: pinned platform archives and SHA-256 checksums from the official scan action, downloaded through the shared network wrapper, extracted with unzip (Unix) or PowerShell Expand-Archive (Windows), then verified using the embedded Java and CLI jar. Managed installation directories are recorded under `dependencies.installed` with id `sonar-scanner`; externally installed scanners are borrowed without registration or removal during reset; `system status` reports their pinned version and `system reset` removes the whole validated install directory. PATH discovery (`scanner-discovery.ts`) verifies scanner version 6.0 or newer and resolves its actual Java runtime, home, and classpath. Unix launchers are probed in offline simulation mode, preserving Homebrew wrapper and JAVA_HOME choices; Windows batch launchers are resolved directly to their distribution and verified with Java, avoiding shell quoting. The first scan invokes that resolved Java directly and passes the auth token through `SONAR_TOKEN`, never process arguments. The authenticated `sonar.host.url` selects the scanner endpoint; `sonar.region` is not passed and inherited `SONAR_REGION` is unset, so the scanner resolves the endpoint from that URL. Proxy/NO_PROXY and TLS settings are translated to scanner environment variables; custom PEM CA bundles are imported through the keytool module using the embedded Java (`-m java.base/sun.security.tools.keytool.Main`), since the scanner runtime omits the standalone keytool executable, and PEM client credentials are converted with the existing PKCS12 helper.

The `hook/`, `context/` and `analyze/` handlers are the runtime half of the agent integrations that install them: `src/commands/integrate/CLAUDE.md` covers both halves and is the file to read before changing either.

To add a new command: add it to `createCommandTree()` in `src/commands/command-tree.ts` and implement the logic in a new folder under `src/commands/`.
Please declare commands using the type defined in `src/core/commands/sonar-command.ts`.
Lifecycle stages (`Stage`) live in `src/core/commands/stage.ts` and are re-exported from `sonar-command.ts`. Qualified invocation paths used in lifecycle warnings live in `src/core/commands/path.ts`.
By default, new commands should register a `authenticatedAction()`; the handler's first argument is a `CommandAuthenticatedInvocationContext` (`auth`, a memoised `connection`, plus stage accessors). `anonymousAction()` receives a `CommandInvocationContext` parent. Both live in `src/core/commands/invocation-context.ts`. Only technical commands use `anonymousAction()`. Handlers resolve credentials through `ctx.resolveAuth()` — memoized on `CliRuntime`'s `AuthResolver`; authenticated handlers also expose `ctx.auth`. Hooks and status paths that must degrade gracefully use `ctx.resolveAuthOrNull()`, or `ctx.resolveConnection()` when they also need a transport: it returns a `SonarConnection` (`auth` plus the `SonarHttpClient` bound to its server, `src/core/server/connection.ts`) or `null` when there are no usable credentials, which is what `ctx.connection` exposes synchronously on the authenticated context. Private Beta entitlement uses `runtime.flagsResolver`. On the context, `isAlphaEligible()` / `isBetaEligible()` answer whether **this execution** should be treated as alpha/beta — not merely whether `.stage()` names that lifecycle (see their own JSDoc in `invocation-context.ts` for the exact conditions). SonarCommand's own `lifecycle` getter is the stage snapshot used for tree visibility and help tags. Handlers record telemetry with `ctx.recordTelemetry(new TelemetryFact(name, payload))`. Facts live on that invocation context (`ctx.telemetryFacts()`), not a tree-owned buffer. `postAction` reads them from the action command's context, resolves the agent session id, then `commitTelemetryFacts` (`src/core/telemetry/index.ts`) emits handler facts concatenated with a `CliCommandExecuted` fact (`buildCommandExecutedFact` in `src/core/telemetry/command-executed.ts`; command/subcommand come from `SonarCommand.commandAndSubcommand()`, `arguments` from `SonarCommand.describeInvocationArguments()`) through generic `emitTelemetryEvent` and schedules the flush. Two root `preAction` hooks run before any handler, in order: Sentry init, then `runPostUpdateActions`.
Mark lifecycle with `.stage(Stage.Stable)` (default), `.stage(Stage.Alpha)`, `.stage(Stage.Beta())` (Open Beta), `.stage(Stage.Beta('cli.beta.flag-key'))` (Private Beta, gated by LaunchDarkly), or `.stage(Stage.Deprecated({ sinceVersion, replacement }))`. Visibility is decided via `CliRuntime` (`isAlphaEnabled` from `SONARQUBE_CLI_ALPHA`, `isPrivateBetaEnabled` from LaunchDarkly). Deprecated commands stay visible and warn on every invocation (`replacement` is required; pass `null` when there is none).
`createCommandTree` builds the tree once (recording Private Beta flag keys as staged commands/options register). Before `parseAsync`, `src/index.ts` calls `runtime.flagsResolver.resolveFlags()` then `refreshStagedVisibility()`. Docs generation calls `createCommandTree({ console })` without resolving flags, so Private Beta stays omitted. Set `SONARQUBE_CLI_LAUNCHDARKLY_ENV=dev` to use the LaunchDarkly `dev` environment (default `production`). Open Beta and Deprecated appear in public docs; Private Beta and Alpha do not.
Contributors stage options with `addOption(new SonarOption('--flag', 'Help').stage(Stage.Alpha))`. Use `.stage(Stage.Beta())` for Open Beta, `.stage(Stage.Beta('cli.beta.flag-key'))` for Private Beta, and `.stage(Stage.Deprecated({ sinceVersion, replacement }))` for Deprecated. Docs include Open Beta and Deprecated options (with badges) and omit Alpha and Private Beta options. Invoking a deprecated command or passing a deprecated option prints a warning every time (`…is deprecated since <version> and will be removed in a future version.` then `Use '<command>' instead.` or `There is no replacement.`).
Visible top-level commands use their main `description()` as root help copy. Every visible top-level command should declare `rootHelp({ category })` so the custom root menu can group commands with blank lines between the `core`, `data`, `integrate`, and `cli-management` sections. The order within each group follows the declaration order in `src/commands/command-tree.ts`, so add or move top-level commands in the desired display order there. When a visible top-level command has visible subcommands, the custom root menu derives its label automatically as `name <sub1|sub2|...>` unless that command also sets `rootHelp({ expandSubcommands: true })`, in which case the parent command is rendered as just `name` and its visible subcommands are listed individually below it. Add `rootHelp({ label })` only when the default label is not enough. If a command should disappear from help entirely, declare it with Commander `{ hidden: true }` and leave an inline comment when hiding a public compatibility command.
The bare `sonar analyze` command accepts `-p, --project <project>` for the agentic portion of the combined flow. Use it to override auto-detection or to run `sonar analyze` without an installed project integration; `--branch` remains specific to `analyze agentic` / `verify`. SQAA accepts `--depth STANDARD|DEEP`: change-set and multi `--file` default to DEEP; single `--file` defaults to STANDARD unless `--depth DEEP` is set. Per-edit hooks force STANDARD; end-of-turn instructions tell agents to always pass `--depth DEEP` (even for a single file).

`sonar quality-gate status`: `src/commands/quality-gate/CLAUDE.md` covers the project-level verdict, branch/PR resolution, and file/directory scoping.

`sonar list issues --file <path>` scopes the search to one file or directory, resolved by `resolveFileComponentKey()` in `src/core/file-component.ts` (shared by any command taking `--file`) — see that file for the resolution mechanics. **Directory scope is intentionally non-recursive**: `GET /api/issues/search`'s `componentKeys` never recurses into subdirectories, verified live against a real project. Enumerating every file under a directory as a workaround was tried and rejected — a real, moderately-sized directory (201 files) already produces a query string the server rejects outright (`414 Request-URI Too Large`), and `issues/search` is GET-only, so there's no way around it. Documented, accepted limitation, not a bug to fix later.

`sonar list issues --format table` and onboarding share `src/commands/list/issues-table.ts`: SEVERITY / FILE:LINE / RULE / MESSAGE columns, full messages wrapped to display width, and a compact stacked layout on narrow terminals. Other list output formats and the JSON default retain their existing response shape.

`sonar list issues` defaults `--statuses` to `OPEN,CONFIRMED` (`DEFAULT_STATUSES` in `src/commands/list/issues.ts`) when the flag is omitted, so results are actionable issues by default rather than the full history including `FIXED`/`FALSE_POSITIVE`/`ACCEPTED`. Pass `--statuses` explicitly to see other states. `-p, --project <project>` is optional: when omitted, the project key is auto-resolved via `resolveProjectKey()`/`discoverProject()` (see "known-server-project-mappings" in `.claude/rules/state-and-auth.md`), same mechanism as `sonar analyze dependency-risks` and `sonar quality-gate status`. `--branch`/`--pull-request` are mutually exclusive; when neither is given, the shared `autoResolvePullRequest()` (`src/core/pull-request-auto-resolve.ts`) tries to match a pull request to the current git branch, printing `Using pull request <id> (auto-detected from branch <branch>)` on a hit. Unlike `quality-gate status`, there's no default-branch fallback: no match leaves both unset and `GET /api/issues/search` applies its own default silently.

`sonar list issues --new-code` limits results to issues found in the new code period (the "leak period"). It shares its Cloud/Server wire-param split with `quality-gate status`'s issue/security breakdowns, which instead derive the value per condition rather than from a direct flag.

`sonar list orgs` (alias `sonar list org`) lists the SonarQube Cloud organizations the authenticated user has access to, via `OrganizationsClient.listUserOrganizations()`; it fails on a Server connection. It supports `--page`/`--page-size` and `--format json|table` like `list projects`, but defaults to `table`. JSON exposes `isAdmin`/`isActive` as separate booleans, built by `toOrganizationSummary()` in `src/core/domain/organization.ts`; the table collapses both into one unlabeled NAME/KEY/status column via `statusLabel()` in `src/commands/list/org.ts`.

`sonar analyze dependency-risks` accepts an optional `-p, --project <project>`. When omitted, the project key is auto-detected via `discoverProject()`.

`sonar analyze dependency-risks` pre-scans discovered manifest files for secrets (via `sonar-secrets`) before the SCA scan and aborts if any are found. In the `analyze` path the secrets binary is a hard prerequisite (install failure aborts the run); in the git pre-commit hook path the manifest secrets _scan_ fails open on a scan error (skips/warns). See `dependency-risk-helpers/manifest-secrets-guard.ts`. This scan-error fail-open is distinct from the git/agent secrets-hook auth+binary gate: an unauthenticated user or a missing `sonar-secrets` binary blocks the commit/push (git hooks throw `MissingDependenciesError` → exit 1).

`sonar import` imports a repository from a connected DevOps platform into SonarQube by provisioning a bound project. The organization is always the one tied to the active connection (`auth.orgKey`), and the CLI verifies the caller is an admin of that org before proceeding. Only organizations bound to GitHub or Azure DevOps can be imported; `assertSupportedAlm()` rejects any other platform before repositories are listed. Accepts exactly one selection-mode flag: `--repo <slug>` (an explicit list — the flag equivalent of interactively choosing "Manual"), `--all` (every eligible repository — equivalent to "Recommended"), or `--regex <regex>` (only eligible repositories whose DevOps platform name, not slug, matches — equivalent to "By pattern"; accepts a `/pattern/flags` literal, e.g. `/^archived-/i`, for flags like case-insensitive matching, since JS has no inline `(?i)` modifier). These three are mutually exclusive; omitting all three interactively shows a Recommended/Manual/By pattern menu. `--non-interactive` requires one of the three. On success it prints the project list link (`{serverUrl}/organizations/{orgKey}/projects`) in the final outro. Implementation lives in `src/commands/import/`.

`sonar link <projectKey>` (barebones — UX will change) writes a single project binding to `.sonar-config.json` at the repository root via the shared `sharedProjectConfigRepository.set()` singleton (see "State and auth" in `.claude/rules/state-and-auth.md` for the file format), overwriting whatever `project` entry was already there. Supports one project per repository; monorepo support is not yet implemented. `<projectKey>` (SonarQube project key) is a positional argument; `--path <path>` (relative to the repo root, defaulting to `.`) is the only option — the server/org come from the active connection (`ctx.auth`), not from flags. `deriveEntryFromAuth()` branches on `auth.connectionType`: `on-premise` writes `serverUrl` as-is; `cloud` derives `region` via `cloudRegionFromUrl(auth.serverUrl)` and uses `auth.orgKey`, failing with `CommandFailedError` if either is unavailable (a Cloud connection with no org is already rejected earlier by `resolveAuth()` itself, so that half of the check is effectively unreachable in practice — the region half remains reachable, e.g. a non-standard Cloud host). `--path` is rejected as `--path must not be empty.` when blank (whitespace-only) — an empty `path` would write successfully but `load()` would then silently and permanently discard the entry via its own `isNonEmptyString` check. `--path` is also validated against the same containment rule `load()` enforces (`resolveContainedPath()`, see "State and auth" in `.claude/rules/state-and-auth.md`), failing with a `CommandFailedError` before writing when it is absolute or escapes the target directory, rather than silently writing an entry that a later `load()` would drop; this validation runs, and any failure is raised, before the no-git-repository warning below, so a rejected path never gets the misleading "Writing to the current directory instead." message. When run outside a git repository, it warns on stderr and writes `.sonar-config.json` to the current directory instead of failing. On success it prints the resolved project root, the project key, the config file's full path, and — only when a git repository was found, since there is nothing to commit otherwise — a hint to commit `.sonar-config.json` to share it. No merge, no removal. Implementation in `src/commands/link/index.ts`.

`sonar stats` (CLI-1113, Alpha) reads the local ledger built by `src/core/stats/` (see that directory's `CLAUDE.md`) and renders the text card or `--json` shape defined in MMF-5834. `--since 7d|14d|30d|all` (default `30d`); the all-time column and `agentBreakdown`/`firstSeenMs` always come from `stats_aggregates`, purge-safe by design. `agentHitRate` is windowed (from surviving `stats_events` rows) except at `--since all`, where it also reads `stats_aggregates`. At `--since all` the windowed breakdowns (`analyzers`/`triggers`/`callerCommandBreakdown`/`topRules`/`topSecretTypes`) also read from `stats_aggregates` instead of `stats_events`, since raw rows past the 1-year retention are gone — `stopped` (secrets-blocked-by-point) is the one exception, with no aggregate dimension of its own, so it can under-count `allTime.secretsBlockedTotal` once old rows are purged (CLI-1115). Query layer: `src/core/stats/stats-queries.ts`/`stats-aggregation.ts`; rendering (sparklines, bars, entitlement placeholders): `src/commands/stats/text-report.ts`.

## System reset

`sonar system reset` returns the CLI to a factory-like state in one shot. Registered as `anonymousAction` so it works when auth is broken. Integration teardown is declarative-only: `integrations.installed` features are removed via `removeFeature()`; legacy `agentExtensions` entries are cleared from state in `clearLegacyState()` but are not used for on-disk cleanup (1.0 does not guarantee removal of pre-declarative artifacts). Binary cleanup removes `dependencies.installed` paths under `BIN_DIR`. `systemReset()` also unconditionally empties the persisted `state.knownServerProjectMappings` table — see "known-server-project-mappings" in `.claude/rules/state-and-auth.md` for why it needs this explicit reset. The local `sonar stats` SQLite ledger (see `src/core/stats/CLAUDE.md`) is wiped outright, as its own reported step (`clearStats()`, `src/commands/system/reset-stats.ts`) rather than folded into the generic filesystem-cache step, per the CLI-1114 ADR. `sonar config` configuration is preserved by default; `--all` removes it as its own step (`clearConfig()`, `src/commands/system/reset-config.ts`): the whole `cli-config.properties` file plus every sensitive key's `config/<key>` keychain entry. Partial reset (step warnings) exits `0`.

`sonar system status` displays a diagnostic overview: authentication (token verified live via `/api/authentication/validate`, four states: Not Set / Active / Invalid / Set Unverified), installed binaries with update availability, configured integrations with paths, and MCP Server configured/running status. Supports `--json` for machine consumption. Implementation in `src/commands/system/status.ts`. Token verification uses `checkTokenStatus` from `src/core/auth/token.ts`; CLI update availability comes from `Distribution/sonarqube-cli/stable.version`, while `sonar update` downloads the platform installer script from the GitHub `user-scripts/` directory when it actually performs the update. MCP config validation is JSON-based for Claude/Copilot (checks `mcpServers.sonarqube` structure) and trusts file existence for Codex TOML configs. A VORTEX section (`src/commands/system/status-vortex.ts`, resolved via `resolveVortexEntitlement` in `src/core/vortex/entitlement.ts`) is shown whenever Vortex is applicable — Cloud with an org, or Server where both the A3S and CAG hub queries answered (a 404 from either hub yields `not_applicable` and hides the section). It reuses `VortexEntitlementClient.hasVortexEntitlement()` (`enabled | over_consumption | not_entitled | check_failed | not_applicable`) rather than re-resolving independently. `src/core/vortex/entitlement.ts` is the single home for Vortex entitlement resolution, named after the domain (not any particular caller): a private `queryVortexEntitlement()` wraps the one client call, and `recheckVortexEntitlement()` (used to reinterpret a runtime 403) and `resolveVortexEntitlement()` (used by `system status`) both call through it; both take the caller's `SonarConnection` as their only parameter instead of building a transport or re-resolving auth, and both return/consume `VortexEntitlementResult` (`src/core/vortex/entitlement.ts`) rather than a separate duplicate type. `not_applicable` covers Cloud-without-org (decided before the API) plus a 404 from either Server hub (returned by `hasVortexEntitlement()` itself). It reports the combined status plus CAG usage (`consumed`/`limit`) only for `enabled`. Only genuine entitlement loss (`not_entitled`, when Vortex is actually applicable) flips the command unhealthy; quota exhaustion (`over_consumption`) and check failures stay healthy.

`sonar self-update` is a deprecated, hidden alias for `sonar update` (only when `CURRENT_DISTRIBUTION.enableSelfUpdate` is true; see `src/core/host/distribution.ts`), staged with `Stage.Deprecated({ sinceVersion: '1.4', replacement: 'sonar update' })`. Calling it prints a deprecation warning, then runs the same `updateVersion()` logic. Both are registered in `src/commands/command-tree.ts`.

`sonar verify` is a deprecated, hidden alias for `sonar analyze` / `analyze agentic`, staged with `Stage.Deprecated({ sinceVersion: '0.14', replacement: 'sonar analyze' })`.

## Cloud onboarding prototype

`sonar auth login --no-organization` stores a Cloud user token without discovering or validating an organization. `--org` conflicts with this flag; ordinary login retains its organization selection. The org-independent state is usable by authenticated commands. `--non-interactive` requires an explicit Cloud server and `--org` or `--no-organization`, opens the browser even in CI, skips terminal prompts, and waits only for a validated callback. It refuses environment-auth conflicts.

`sonar org import --github <owner> --plan team-trial` reuses an administrable GitHub binding or finds/installs the GitHub App, creates and binds a Cloud organization with the existing v1 API, starts a cardless Team trial when absent (default `team-trial`; explicit `free` retains zero-cost Free signup), and selects the org. Existing subscriptions are preserved. Supports `--key`, `--installation-id`, `--no-browser`, `--timeout`, and `--format text|json`. The JSON result exposes `organizationKey`, `github`, `plan`, and `url`; browser instructions go to stderr. No backend endpoints were added.

`sonar project wait --repo <owner/repo>` resolves the real linked project in the active organization; `--project` selects a key directly and is required for monorepos. It requests auto-enable eligibility only when no completed analysis exists, handles empty HTTP 202 responses, and polls `/api/project_analyses/search`. JSON exposes `projectKey`, `analysisId`, `analysisDate`, and `url`. It does not guarantee the analyzed revision matches local changes. Unsupported automatic analysis errors with CI guidance; timeouts are resumable. Shared transport/domain API calls are in `core/server/cloud-onboarding.ts`; sequential polling is in `core/commands/poll.ts`.

Portable agent instructions are in `skills/sonarcloud-onboard/SKILL.md`. The prototype must be built locally or supplied as a compatible binary; a current stable download may lack these commands. Integration tests cover the full flow using local HTTP fixtures and the standard isolated TestHarness, with no live Cloud mutations.

`auth login --force` skips saved-token reuse and starts a fresh browser exchange. Existing saved credentials are replaced only after successful validation and organization resolution. This is needed when switching an SSO connection to GitHub for organization onboarding. The legacy installation-discovery endpoints require a GitHub/Bitbucket identity; an SSO user resolves to `OTHER` and gets HTTP 400. `org import` identifies the failing discovery step and prints the server explanation. GET 400 responses now use the shared structured-error parser, which also recognizes v1 `errors[].msg`.

Free-plan selection matches `/billing/plans`'s top-level `name` (`Free_v2`, case-insensitive), then verifies all currency amounts are zero. The live response does not supply `tiers[].metadata`; do not depend on it. The separate legacy `Free` (OSS) plan must not be selected. GitHub redirects to the normal Cloud onboarding UI after App installation, but the CLI independently completes subscription signup; no browser plan-selection step is required.

For an organization freshly created by `org import`, create the subscription before reading `/billing/subscriptions`, matching web onboarding. On reused organizations, keep the existing-subscription lookup and propagate authorization errors; a 403 is never interpreted as absence. Organization-ID and billing errors identify the failed endpoint.

## Guided browser handoffs

`auth login --non-interactive --no-browser --events` prepares a sign-in URL and holds the loopback callback open. `org import --no-browser --events` prepares GitHub access and holds the installation poll open. Both emit versioned `browser_required`, `step_started`, `step_completed`, and `step_failed` JSON events on stderr alongside diagnostics. stdout retains normal output or the final JSON result. The agent reads an action, explains it, then runs `sonar browser open <url>`; the original command must keep running. `project wait --events` reports analysis progress without changing its result JSON. Browser opening is a technical anonymous command accepting HTTP(S) URLs without credentials or control characters.

The shared reporter is `core/commands/onboarding-progress.ts`. Login validates reused tokens; invalid saved credentials trigger a fresh exchange, and unreachable validation aborts. Browser-only callback validation failures reject even outside CI. Ordinary invocations retain automatic browser opening; auth events require both `--non-interactive` and `--no-browser`, and org events require `--no-browser`.

Cardless Team trials use POST /billing/subscriptions with email and no priceId, card or address. Verify planKey=team and active status case-insensitively (dev9 returns Team/active), trial=true, valid trialPeriod and GET /billing/customers paymentMethodStatus=NONE. Return trial/status/period in org JSON. Preserve existing subscriptions and propagate rejected trials without paid fallback.

Organization import reuses an administrable unbound organization at the requested/default key and binds its existing installation via POST /api/alm_integration/bind_organization. It preserves subscriptions and rejects replacing an unrelated binding.

# State and auth

- Persistent state (server URL, org, project) is managed via `src/core/state/state-manager.ts`.
- `loadState()` returns defaults only when `state.json` is absent; if an existing file fails to read/parse it retries then throws (so `saveState()` can't wipe a corrupt file — CLI-834). Best-effort callers (Sentry init, `commitTelemetryFacts`/`flushTelemetry`, `runPostUpdateActions`) use `tryLoadState()`, which returns `null` on failure.
- Declarative integration installs are tracked as integration entries in the top-level `integrations.installed` state registry, with installed feature targets nested under each integration. Shared declarative dependencies (for example SonarSource binaries required by multiple features) are recorded separately in `dependencies.installed` and referenced from features by id. Every binary install records there via `recordInstalledDependency()`, including installs outside the framework (`sonar analyze secrets`, `analyze dependency-risks`), always under the declared (pinned) version rather than the binary's self-reported one. This is the generic state surface for Git, Claude, Codex, Copilot, Antigravity, and future integrations; legacy `agents` and `agentExtensions` remain for compatibility. The legacy `tools.installed` registry is retired: `migrateState()` folds its entries into `dependencies.installed` on load.
- **`state.knownServerProjectMappings`** (`KnownServerProjectMapping[]`, each `{ targetRoot, repoRoot?, projectKey, serverUrl?, orgKey? }`) is the persisted half of `discoverProject()`'s fast path. `targetRoot` and `repoRoot` are two distinct signals copied verbatim from a feature's own `targetRoot`/`attrs.repoRoot` — never collapsed into one value — so two worktrees of the same repo, integrated with different project keys, stay distinguishable even though both may share the same recorded `repoRoot`. `serverUrl`/`orgKey` are recorded-only (undefined when the contributing feature never recorded a connection, e.g. `git` integrate) — deliberately **not** backfilled from the active connection here, since that would bake a point-in-time snapshot into a mapping matched by a possibly much later, possibly different-environment invocation (env-var auth can switch server/org per invocation). `src/core/known-server-project-mappings.ts` (a top-level `core/` module, not `core/state/`, since it holds domain logic rather than generic state models/helpers) owns `mergeKnownServerProjectMappings` and `buildKnownServerProjectMappings(state)`, which derives mappings by parsing `attrs.projectKey`/`serverUrl`/`orgKey` verbatim off every currently project-scoped `integrations.installed` feature. Both are built on `upsertMapping`: two mappings collapse only when they share both `targetRoot` and `projectKey` — a true duplicate, kept as whichever has server info. A same-`targetRoot`/different-`projectKey` pair is a genuine conflict, not a duplicate — both are kept as separate candidates for `selectFeatureForLookupPaths` (`src/core/host/recorded-feature-resolver.ts`) to resolve at match time (whichever came first wins, deliberately not based on recency — a feature's `updatedAt` is refreshed on every post-update reconcile pass regardless of content, so it was never a meaningful signal). A `targetRoot` absent from a fresh pass is never dropped. There is no explicit "record a mapping" write path — project-scoped integrations are being phased out in favor of global scope (CLI-878), so persisting this table is deliberately migration-driven rather than something every integrate action maintains by hand. Two things keep the table current:
  - **`src/core/update/known-project-mappings-migration.ts`** calls `buildKnownServerProjectMappings(state)` and merges the result into the persisted table via `mergeKnownServerProjectMappings` on every post-update run. It runs _before_ `migrateDeclarativeIntegrations` specifically so it can capture this data from integrations that are about to be reconciled to global scope and permanently lose their per-folder attrs; once that happens, this table is the only place the fact survives.
  - **A live fallback inside `discoverProject()` itself** — when the persisted table has no match, it calls `buildKnownServerProjectMappings(state)` again, live, so a project integrated since the last CLI upgrade still resolves before the next post-update migration runs. That fallback naturally stops finding anything once all integrations are global-scoped.

  Both the persisted table and the live fallback are matched the same way: `src/core/host/git/lookup-path-resolver.ts`'s `resolveLookupPaths(startDir)` builds one explicit, nearest-first list of directories to check — startDir climbing to the repo root (git) or the filesystem root (non-git), plus, from a linked worktree, a second climb over the main working tree's offset-equivalent path — and `selectFeatureForLookupPaths` (`src/core/host/recorded-feature-resolver.ts`) walks that list checking each candidate's `targetRoot` then `repoRoot` for an exact match, ties broken by whichever candidate came first (duplicates are already resolved upstream by `upsertMapping`). This is the same shared policy SQAA/CAG project-key lookups use (see "Agent SQAA delivery" in `src/commands/integrate/CLAUDE.md`).

  **`.sonar-config.json`** is a small, git-committed file naming one project binding, so a team doesn't rely on everyone re-running `sonar integrate` or hand-authoring SonarLint bindings — a repo with multiple projects needs one file per project directory. `src/core/shared-project-config.ts` owns the resolved model (`SharedProjectConfigMapping`), the `SharedProjectConfigRepository` interface, its file-backed `SharedProjectConfigRepositoryImpl`, the write/read entry shape `SharedProjectConfigEntry`, and the shared `sharedProjectConfigRepository` singleton that `project-info.ts` and `sonar link` both use (one instance so tests `spyOn` the same object) — `load(dir)` reads `<dir>/.sonar-config.json` (`SHARED_PROJECT_CONFIG_FILE_NAME`) as `{ project: {...} }` — the mapping lives nested under a `project` key rather than at the file's root, so other top-level fields can be added later without disturbing it — resolving `project`'s relative `path` into an absolute `projectRoot`, and (Cloud entries) `region`+`organization` into `serverUrl` via `cloudRegionToUrl()` (`src/core/server/sonarcloud-region.ts`). `load()` returns `null` when the file is missing, unparseable, an array (the old multi-entry shape), missing/invalid `project`, or otherwise invalid — including when `path` is absolute, resolves outside `dir`, does not exist on disk, or is not a directory (`resolveContainedPath()`), since a committed config is untrusted input and `projectRoot` later drives write/delete/mount targets (`sonar link` rejects the same escaping/missing/non-directory paths up front, see `src/commands/CLAUDE.md`). Requiring the resolved path to exist is also what keeps `resolveContainedPath()` safe against a symlinked intermediate directory (e.g. a committed `path: "vendor/evil"` where `vendor` is a symlink escaping `dir`): `canonicalizePath()` only reliably resolves symlinks via `realpathSync.native` when the full path exists, otherwise it falls back to a purely lexical `resolve()` that leaves symlinks untouched — so requiring existence up front sidesteps that gap entirely rather than needing a separate partial-resolution helper. `set(dir, entry)` merges into the existing root rather than replacing it wholesale — it reads and parses the current file first and spreads the new `project` entry over it, preserving any other top-level fields already there — and fails closed on that read: a genuinely missing file is treated as an empty root, but any other read error or invalid/unparseable JSON aborts the write instead of silently clobbering content it couldn't safely merge into.

  `discoverProject()` (`src/core/project-info.ts`) resolves each `DiscoverProject` call through four sources in turn, the first three walking that _same_ lookup-path list so "closer wins" is uniform regardless of which source matches: (1) shared project config — climbs to the first directory holding a `.sonar-config.json` (stop-at-first-hit, like the local-config check below) and applies it unconditionally once found — one file holds exactly one mapping, so there is no "found but doesn't match" case; `projectRoot` becomes the entry's own `path`, resolved relative to the directory the file was found in, which need not be the invocation directory; (2) known-server-project-mapping (persisted table, then the live fallback) at every lookup path; (3) `sonar-project.properties`/`.sonarlint`, also checked at every lookup path in the same nearest-first order (so a monorepo subpackage's own properties file is found before an ancestor's); (4) git-remote binding, a single non-climbed last resort scoped to the whole repository. Whichever source resolves the `projectKey` sets `DiscoveredProject.projectRoot` to the exact directory that matched (defaulting to `repoRoot` when nothing matches) — `repoRoot` stays "what repo/directory am I in" (the git top-level, or the raw invocation directory outside git), while `projectRoot` is "where is the discovered project anchored," which is routinely a subdirectory of `repoRoot` (a monorepo's project does not have to sit at the repo root). This is not just a CAG nicety: every agent-integrate call site that decides _where on disk to act_ — `resolveIntegrateInstallTarget` / `resolveIntegrateScope` (`agent-integrate-prelude.ts`), the preflight summary's `Root` line (`preflight-summary.ts`), `removeObsoleteHookArtifacts` (`claude/index.ts`), and the MCP filesystem-mount root (`run/mcp.ts`) — also reads `project.projectRoot`, not `repoRoot`, so integrating from inside a monorepo subpackage follows that subpackage instead of always bubbling up to the git top-level; `sonar context`'s workspace-dir resolution relies on the same field for the same reason. `serverUrl`/`orgKey` are required on the mapping (despite not always being explicitly recorded) because `warnAuthProjectMismatches()` (`agent-integrate-prelude.ts`) reads `DiscoveredProject.serverUrl`/`.organization` to warn when the active auth connection disagrees with a project's recorded one, and a cache hit that left those fields empty would silently disable that check on every repeat `sonar integrate` of an already-mapped folder.

- Tokens are stored in the system keychain via `src/core/host/keychain.ts` — never store tokens in plain files.
- **Env-var auth records state exactly like `sonar auth login`, minus the keychain write (CLI-866).** `resolveAuth()` (`src/core/auth/auth-resolver.ts`) is `resolveFromEnv() ?? resolveFromState()`; whenever the env branch resolves, it calls `recordConnectionFromAuth()` (`src/core/auth/auth-connection-recorder.ts`) before returning. That helper is the same state-writing step `sonar auth login` uses: `addOrUpdateConnection()` (server/org/region/tokenName) plus identity enrichment via `resolveTelemetryIdentity()` (`src/core/telemetry/identity-fetch.ts`) — it just never calls `saveToken()`, since env-var auth exists specifically for sandboxed/headless environments (CLI-692) that cannot access the keychain in the first place. It no-ops (no state write, no network call) when the active connection already matches the resolved auth and its identity is already complete (`needsIdentityEnrichment()`), and accepts `force: true` to bypass that check — used by `login.ts` itself, since an explicit `sonar auth login` must always refresh `authenticatedAt`/`tokenName` even when re-authenticating to an already-known connection. `resolveAuth({ silent: true })` suppresses the "partial env vars" warning for callers (telemetry) that must not surface a diagnostic on every command. `src/core/server/sonarcloud-region.ts` holds the pure URL/region helpers (`cloudRegionFromUrl`, `resolveFromEndpoint`, etc., re-exported from `auth-resolver.ts` for compatibility) that both `auth-resolver.ts` and `identity-fetch.ts` need, without creating an import cycle between the two.
- All path and URL constants live in `src/core/config-constants.ts` — import from there instead of hardcoding.
- Shared Sonar product data lives under `~/.sonar`; CLI-specific data stays under `~/.sonar/sonarqube-cli`, and the stable anonymous telemetry user ID is shared at `~/.sonar/user`. `SONAR_USER_HOME` is only a late-bound override for state persistence and telemetry user-id codepaths; other exported path constants remain fixed after import.
- Caller-agent hints (Cursor, Claude Code, Copilot CLI, Codex, or Antigravity) from the environment: `src/core/host/environment/agent-detector.ts` (`detectCallerAgent`, etc.) — distinct from `installed-agent-detector.ts` (`detectInstalledAgents`) in the same directory, which detects installed agents rather than the caller.
- `sonar auth logout` relies on state: if there is no active connection or `isAuthenticated` is false, it only reports that you are already logged out (no keychain changes).
- When `sonar auth login` runs the browser-based OAuth flow, the server-generated token name returned in the callback POST body is captured and persisted on the connection as `tokenName` (see `AuthConnection` in `src/core/state/state.ts`). The wire field is `name` (matching `/api/user_tokens/revoke?name=`); we keep it as `tokenName` in-memory to disambiguate from other "name" fields.
- On `sonar auth logout`, the CLI best-effort revokes the server-side token via `UsersClient.revokeUserToken(...)` (a one-line wrapper over the generic `postForm(endpoint, params)` helper) before clearing the keychain entry. Failures (network error, non-2xx response) are reported via a warning on stderr; local cleanup still proceeds. When the connection has no `tokenName` (e.g. upgraded from an older CLI version), the CLI emits a manual-revocation hint on stderr instead. `revokeServerTokenIfPossible` takes a `RevocableToken` (`Pick<AuthConnection, 'serverUrl' | 'tokenName'>`) rather than a full connection, so `login` can reuse it before any connection exists.
- **On SonarQube Cloud, `sonar auth login` validates every organization key it is given (CLI-129).** `--org`, a key found in project config, and a hand-typed key are all resolved against the server. Keys picked from the membership menu are not re-checked: the server supplied them. SonarQube Server has no organizations, so `--org` is dropped up front on a Server connection and `resolveOrganization()` returns `undefined` there. Dropping it before the keychain lookup matters: the keychain account is derived from the organization, so a kept `--org` would make the next login miss the token it just saved. Validation calls `OrganizationsClient.resolveOrganizationAccess()`, which returns `accessible | not_found | check_failed` (`OrganizationAccess`, same shape as `VortexEntitlementStatus`). The three states matter: `/api/organizations/search` answers an unknown key with `200` and an empty list, so an error never means absence. Reporting one as "not found" was the old defect. `isOrganizationAccessible()` keeps its boolean contract for `integrate`'s preflight by delegating to the same resolver. The `organizations=<key>` filter is not membership-scoped and resolves public organizations, which is what makes validating a hand-typed key safe; never validate manual entry with `listUserOrganizations()` (`member=true`), `actions.admin`, or a project listing. `listUserOrganizations()` no longer swallows errors either, so an outage cannot look like "you belong to no organization". A rejected key does not have to cost the browser flow that just ran, so each source decides whether it can offer a way out. `--org` always aborts (nothing to fall back to). A hand-typed key or an empty line is warned about and asked again, bounded by `MAX_ORGANIZATION_ATTEMPTS` so a terminal that never answers ends on the existing error instead of looping — and only on a TTY, since piped input has nobody to ask. A stale key in project config falls through to `getUserSelectedOrganization()` on **any** stdin, TTY or not: that lookup resolves a single membership without asking anything, so gating it on a TTY would fail a login that needed no interaction. Only `check_failed` always aborts, since asking again cannot fix an outage. When login does fail, it revokes the token it just minted (`discardGeneratedToken`), so a typo leaves no orphan token; a reused keychain token, or one pasted by hand (no `tokenName`), is left alone. Validation runs **after** token generation on purpose: resolving a private organization needs a token, so checking first would break the members-only case.

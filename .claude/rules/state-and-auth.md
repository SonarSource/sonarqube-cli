# State and auth

- Persistent state (server URL, org, project) is managed via `src/core/state/state-manager.ts`.
- `loadState()` returns defaults only when `state.json` is absent. If an existing file fails to read or parse, it retries and then throws so an update cannot erase unreadable state. Best-effort callers (`buildIdentityBase`, `runPostUpdateActions`) use `tryLoadState()`, which returns `null` on failure.
- `updateState(fn)` is the only state write path. It takes a SQLite immediate-transaction lock, reads the latest state, applies the synchronous callback, and atomically replaces `state.json` after an `fsync`. A corrupt lock database stops the update and reports how to repair the lock after all CLI processes stop. Transient Windows replacement errors are retried for a short, bounded period. An interrupted write leaves the previous complete state readable. A callback failure leaves the file unchanged. Auth identity lookup, integration installation, and post-update reconciliation finish slow work before their final callback. Integration saves apply recorded feature changes by integration id, feature id, scope, and target root against the latest state; two processes creating the same integration and target produce one entry.
- Declarative integration installs are tracked as integration entries in the top-level `integrations.installed` state registry, with installed feature targets nested under each integration. Shared declarative dependencies (for example SonarSource binaries required by multiple features) are recorded separately in `dependencies.installed` and referenced from features by id. Every binary install records there via `recordInstalledDependency()`, including installs outside the framework (`sonar analyze secrets`, `analyze dependency-risks`), always under the declared (pinned) version rather than the binary's self-reported one. This is the generic state surface for Git, Claude, Codex, Copilot, Antigravity, and future integrations; legacy `agents` and `agentExtensions` remain for compatibility. The legacy `tools.installed` registry is retired: `migrateState()` folds its entries into `dependencies.installed` on load.
- **`state.knownServerProjectMappings`** (`KnownServerProjectMapping[]`, each `{ targetRoot, repoRoot?, projectKey, serverUrl?, orgKey? }`) is the persisted half of `discoverProject()`'s fast path. `targetRoot` and `repoRoot` are two distinct signals copied verbatim from a feature's own `targetRoot`/`attrs.repoRoot` — never collapsed into one value — so two worktrees of the same repo, integrated with different project keys, stay distinguishable even though both may share the same recorded `repoRoot`. `serverUrl`/`orgKey` are recorded-only (undefined when the contributing feature never recorded a connection, e.g. `git` integrate) — deliberately **not** backfilled from the active connection here, since that would bake a point-in-time snapshot into a mapping matched by a possibly much later, possibly different-environment invocation (env-var auth can switch server/org per invocation). `src/core/project-discovery/known-server-project-mappings.ts` (not `core/state/`, since it holds domain logic rather than generic state models/helpers) owns `mergeKnownServerProjectMappings` and `buildKnownServerProjectMappings(state)`, which derives mappings by parsing `attrs.projectKey`/`serverUrl`/`orgKey` verbatim off every currently project-scoped `integrations.installed` feature. Both are built on `upsertMapping`: two mappings collapse only when they share both `targetRoot` and `projectKey` — a true duplicate, kept as whichever has server info. A same-`targetRoot`/different-`projectKey` pair is a genuine conflict, not a duplicate — both are kept as separate candidates for `selectFeatureForLookupPaths` (`src/core/host/recorded-feature-resolver.ts`) to resolve at match time (whichever came first wins, deliberately not based on recency — a feature's `updatedAt` is refreshed on every post-update reconcile pass regardless of content, so it was never a meaningful signal). A `targetRoot` absent from a fresh pass is never dropped. There is no explicit "record a mapping" write path — project-scoped integrations are being phased out in favor of global scope (CLI-878), so persisting this table is deliberately migration-driven rather than something every integrate action maintains by hand. Two things keep the table current:
  - **`src/core/update/known-project-mappings-migration.ts`** calls `buildKnownServerProjectMappings(state)` and merges the result into the persisted table via `mergeKnownServerProjectMappings` on every post-update run. It runs _before_ `migrateDeclarativeIntegrations` specifically so it can capture this data from integrations that are about to be reconciled to global scope and permanently lose their per-folder attrs; once that happens, this table is the only place the fact survives.
  - **A live fallback inside `discoverProject()` itself** — when the persisted table has no match, it calls `buildKnownServerProjectMappings(state)` again, live, so a project integrated since the last CLI upgrade still resolves before the next post-update migration runs. That fallback naturally stops finding anything once all integrations are global-scoped.

  Both the persisted table and the live fallback are matched the same way: `src/core/host/git/lookup-path-resolver.ts`'s `resolveLookupPaths(startDir)` builds one explicit, nearest-first list of directories to check — startDir climbing to the repo root (git) or the filesystem root (non-git), plus, from a linked worktree, a second climb over the main working tree's offset-equivalent path — and `selectFeatureForLookupPaths` (`src/core/host/recorded-feature-resolver.ts`) walks that list checking each candidate's `targetRoot` then `repoRoot` for an exact match, ties broken by whichever candidate came first (duplicates are already resolved upstream by `upsertMapping`). This is the same shared policy SQAA/CAG project-key lookups use (see "Agent SQAA delivery" in `src/commands/integrate/CLAUDE.md`).

  **`.sonar-config.json`** is a small, git-committed file naming one or more project bindings, so a team doesn't rely on everyone re-running `sonar integrate` or hand-authoring SonarLint bindings. `src/core/project-discovery/shared-project-config.ts` owns the resolved model (`SharedProjectConfigMapping`), the `SharedProjectConfigRepository` interface, its file-backed `SharedProjectConfigRepositoryImpl`, the write/read entry shape `SharedProjectConfigEntry`, and the shared `sharedProjectConfigRepository` singleton that `project-info.ts` and `sonar link` both use (one instance so tests `spyOn` the same object). The file root holds either a legacy singular `project` (one mapping) or a `projects` array (several, for a monorepo) — `projects` takes precedence when both are present — the mapping(s) live nested under these keys rather than at the file's root, so other top-level fields can be added later without disturbing them. `load(dir)` reads `<dir>/.sonar-config.json` (`SHARED_PROJECT_CONFIG_FILE_NAME`) and resolves every entry it finds, always as a list (`[]` when the file is missing/unparseable/invalid) — the only method on the interface, so no caller has to decide up front whether it's reading a legacy singular `project` or a monorepo `projects` array. Each entry resolves independently: its relative `path` into an absolute `projectRoot`, and production Cloud entries with `region`+`organization` into `serverUrl` via `cloudRegionToUrl()` (`src/core/server/sonarcloud-region.ts`); custom Cloud entries retain `serverUrl`+`organization` so a staging or other non-default host does not resolve to a production URL. An individually-invalid entry inside `projects` is skipped (debug-logged) without dropping the others. It returns nothing when the file is missing, unparseable, an array at the root (the old multi-entry shape, now superseded by `projects`), or an entry's `path` is absolute, resolves outside `dir`, does not exist on disk, or is not a directory (`resolveContainedPath()`), since a committed config is untrusted input and `projectRoot` later drives write/delete/mount targets (`sonar link` rejects the same escaping/missing/non-directory paths up front, see `src/commands/CLAUDE.md`). Requiring the resolved path to exist is also what keeps `resolveContainedPath()` safe against a symlinked intermediate directory (e.g. a committed `path: "vendor/evil"` where `vendor` is a symlink escaping `dir`): `canonicalizePath()` only reliably resolves symlinks via `realpathSync.native` when the full path exists, otherwise it falls back to a purely lexical `resolve()` that leaves symlinks untouched — so requiring existence up front sidesteps that gap entirely rather than needing a separate partial-resolution helper. `set(dir, entry)` merges into the existing root rather than replacing it wholesale — it reads and parses the current file first and spreads the new `project` entry over it, preserving any other top-level fields already there (including an existing `projects` array, which `set()` leaves untouched) — and fails closed on that read (`addProject(dir, entry)`, used by `sonar link --monorepo`, is the `projects`-array counterpart: it upserts by canonical directory, keeps any singular `project`, and fails closed the same way, additionally rejecting a non-array `projects`): a genuinely missing file is treated as an empty root, but any other read error or invalid/unparseable JSON aborts the write instead of silently clobbering content it couldn't safely merge into.

  **`discoverProjectMappings()`** (private, `src/core/project-discovery/project-info.ts`) resolves every project mapping for a directory into a `ProjectDiscoveryResult` (`{ repoRoot?, projects: ProjectMapping[], scope(path) }`, in its own `project-discovery/project-discovery-result.ts`) — `ProjectMapping` is `CompleteProjectMapping | PartialProjectMapping`: `CompleteProjectMapping` (`{ projectRoot, projectKey, serverUrl, organization? }`) is a fully resolved binding — both fields present; `PartialProjectMapping` (`{ projectRoot, projectKey?, serverUrl?, organization? }`) is what a single-valued source may resolve instead, not guaranteed to carry both, and exists only to support `discoverProject()`'s own fallback. It tries four sources in order: (1), tried directly in `discoverProjectMappings()` itself, is shared project config (`.sonar-config.json`) — the **only** multi-valued source, since its `projects` array is the one place more than one match can come from, and always a `CompleteProjectMapping` since every entry it accepts already requires both `projectKey` and `serverUrl`. When that resolves nothing, it delegates to `discoverProjectWithoutSharedConfig()` for (2)-(4): known-server-project-mapping (persisted table + live fallback, in `project-discovery/known-server-project-mapping-resolution.ts`/`known-server-project-mappings.ts`) — also always complete, since `applyKnownServerProjectMapping` only succeeds once it has resolved a usable `serverUrl` to go with the mapping's `projectKey`; `sonar-project.properties`/`.sonarlint` (`project-discovery/local-project-config.ts`); and git-remote binding (`server/discover-project-by-remote.ts`, kept outside `project-discovery/` as an API-client wrapper per `.claude/rules/sonarqube-api.md`). Only local config can land on just a `projectKey` with no `serverUrl`: a SonarQube Cloud `sonar-project.properties`/`.sonarlint` binding conventionally omits the host URL, since a Cloud region's URL is well-known rather than per-project data — the connection is really `{serverUrl}` for SonarQube Server vs. `{region, organization}` for Cloud, `serverUrl` merely being how Cloud's resolved form happens to be represented too. `loadSonarProperties()` (`local-project-config.ts`) derives the missing host URL from `sonar.organization` via `cloudRegionToUrl('eu')` the same way `.sonarlint`'s own parser already derives it from `sonarCloudOrganization` (`core/host/sonarlint-connected-mode.ts`'s `sonarCloudBaseUrlFromRegion()`) — never from the invocation's `auth`, which is an unrelated signal (a different, even mismatched, active connection) and would give the wrong answer once a monorepo caller reads `serverUrl`/`organization` as genuine per-project data instead of assuming a single global connection. A `sonar.host.url` that's present but invalid, with no `organization` to derive from, is left unresolved — there's nothing to derive it from. `scope(path)` filters `projects` to those on the same ancestry line as `path` (directory or file) via `isAncestorOrSelf()`, no nearest-wins, and tags each with `contains` (`ScopedProjectMapping`): whether its root is `path` or encloses it, rather than sitting below it.

  **`discoverProjects()`** (exported) is the only public entry point onto this machinery: it wraps `discoverProjectMappings()` and filters `.projects` down to `isCompleteProjectMapping()` matches, returning a `DiscoveredProjects` (same `project-discovery-result.ts` file; `{ repoRoot?, projects: CompleteProjectMapping[], scope(path), mappingFor(path), groupByMapping(paths) }`) — `PartialProjectMapping` never leaves `project-info.ts`. Where `scope()` keeps every mapping on the same ancestry line, `mappingFor(path)` is its nearest-wins counterpart for callers that fan work out per project (monorepo SQAA/SCA): the mapping with the deepest `projectRoot` that contains `path` (ties keep the first in file order), matched lexically on canonicalized paths so a deleted file still resolves. `groupByMapping(paths)` applies it per path and returns `{ groups: { mapping, paths }[], unmapped }`, with groups in first-seen order and paths exactly as given. **`discoverProject()`** (singular) scopes the internal discovery result to the invocation directory and collapses complete mappings to one project — a match counts only when it carries both `projectKey` and `serverUrl`, since that's what `resolveProjectKey()` and every other "give me the project" caller needs. A `sonar-project.properties` with just a project key — no organization to derive a Cloud URL from, no (valid) host URL — therefore resolves to nothing via `discoverProject()`, even though the same partial match is still useful to `discoverServer()`/`discoverOrganization()` — those two never read `projectKey` at all, so they go through a separate, partial-tolerant path (`discoverLocalConfig()` in `project-info.ts`, built on the private `discoverProjectMappings()` + `scope()` directly, since it needs the `PartialProjectMapping` case the public `discoverProjects()` hides) that accepts whichever single field a match did resolve. The singular result also exposes `hasSonarConfig` from scoped partial or complete mappings and `gitRemoteBindingNotFound` only after a successful authenticated empty remote lookup. Session-start hooks use these signals for recovery warnings without exposing incomplete mappings as resolved projects. Zero complete matches and more than one complete match both degrade to "nothing resolved" (project key and connection fields undefined) — ambiguous and missing are the same unusable answer to every current caller, so `discoverProject()` never throws: hooks run unattended and can't act on an exception, and the few commands with a real `--project` flag already print one generic "could not determine project key" error either way. `projectRoot` anchors to the matched mapping's directory (the invocation directory when nothing matched) — distinct from `repoRoot`, the git top-level; a monorepo project routinely sits below it. Agent integrations no longer discover a project at install time (see "Agent SQAA delivery" in `src/commands/integrate/CLAUDE.md`), so `projectRoot` now matters at runtime to `sonar integrate git`, `sonar context`'s workspace-dir resolution, and the MCP mount root (`run/mcp.ts`).

- Tokens are stored in the system keychain via `src/core/host/keychain.ts` — never store tokens in plain files. The account is the server hostname only: the CLI ignores port, path and organization, so the check on the normalized server URL recorded in state is what tells servers on one host apart. A token an older CLI stored under `hostname:org` moves to the hostname account once, in the post-update step `migrateLegacyKeychainTokens`; it must run before the migrations that resolve auth. The move runs once: if it fails, the CLI warns and does not retry, and no command removes the leftover `hostname:org` entry. A stored token is reused during login only when state records a non-environment-only connection to the same normalized server URL (origin and base path). For a new or already environment-only connection, env-var auth records it as keychain-backed only when its token equals the stored token; an unreadable keychain counts as no match. A matching login-created connection stays keychain-backed even when the env token differs or the keychain is unavailable. Stored-auth resolution skips environment-only connections. `sonar context` uses the active token whenever the recorded server, compared by normalized URL, equals the active server. Sensitive `sonar config` values share the keychain service under `config/<key>` accounts. Non-sensitive ones go to `cli-config.properties` in the CLI dir, with literal values (backslashes are not escapes); `src/core/config/config-repository.ts` routes each key by its schema sensitivity. `src/core/host/connectivity/network-config.ts` reads the `network.*` keys as the tier between `SONAR_*` and generic env vars, treating an unreadable store as unset. `src/core/observability/logger-config.ts` reads `log.level` at startup, below `LOG_LEVEL`.
- **Env-var auth records state exactly like `sonar auth login`, minus the keychain write (CLI-866).** `AuthResolver` (`src/core/auth/auth-resolver.ts`) memoizes resolution per CLI process; handlers reach it through `ctx.resolveAuth()`. On the env-var path it calls `recordConnectionFromAuth()` (`src/core/auth/auth-connection-recorder.ts`) before returning. That helper is the same state-writing step `sonar auth login` uses: `addOrUpdateConnection()` (server/org/region/tokenName) plus identity enrichment via `resolveTelemetryIdentity()` (`src/core/telemetry/identity-fetch.ts`) — it just never calls `saveToken()`, since env-var auth exists specifically for sandboxed/headless environments (CLI-692) that cannot access the keychain in the first place. It no-ops (no state write, no network call) when the active connection already matches the resolved auth and its identity is already complete (`needsIdentityEnrichment()`), and accepts `force: true` to bypass that check — used by `login.ts` itself, since an explicit `sonar auth login` must always refresh `authenticatedAt`/`tokenName` even when re-authenticating to an already-known connection. `sonar auth org` also passes `force: true`, and it must pass the active connection's `tokenName`: the recorder drops `tokenName` unless the caller gives it, and without it `sonar auth logout` can no longer revoke the token on the server. `ctx.resolveAuth({ silent: true })` suppresses the "partial env vars" warning for callers (telemetry) that must not surface a diagnostic on every command. Callers that need git-remote binding in `discoverProject()` must resolve auth first (for example via `ctx.resolveAuth()`) and pass it as `auth`; pre-login discovery passes `useKnownMappings: false` so known mappings do not short-circuit prompts.
- All path and URL constants live in `src/core/config-constants.ts` — import from there instead of hardcoding.
- Shared Sonar product data lives under `~/.sonar`; CLI-specific data stays under `~/.sonar/sonarqube-cli`, and the stable anonymous telemetry user ID is shared at `~/.sonar/user`.
- Caller-agent hints (Cursor, Claude Code, Copilot CLI, Codex, Antigravity, OpenCode, or Pi) from the environment: `src/core/host/environment/agent-detector.ts` (`detectCallerAgent`, etc.) — distinct from `installed-agent-detector.ts` (`detectInstalledAgents`) in the same directory.
- When `sonar auth login` runs the browser-based OAuth flow, the server-generated token name returned in the callback POST body is captured and persisted on the connection as `tokenName` (see `AuthConnection` in `src/core/state/state.ts`). The wire field is `name` (matching `/api/user_tokens/revoke?name=`); we keep it as `tokenName` in-memory to disambiguate from other "name" fields. Set `SONARQUBE_CLI_DISABLE_BROWSER=true` to keep the loopback callback and manual token entry available without opening a browser; the integration harness sets this by default.
- On `sonar auth logout`, the CLI best-effort revokes the server-side token via `UsersClient.revokeUserToken(...)` (a one-line wrapper over the generic `postForm(endpoint, params)` helper) before clearing the keychain entry. Failures (network error, non-2xx response) are reported via a warning on stderr; local cleanup still proceeds. When the connection has no `tokenName` (e.g. upgraded from an older CLI version), the CLI emits a manual-revocation hint on stderr instead. `revokeServerTokenIfPossible` takes a `RevocableToken` (`Pick<AuthConnection, 'serverUrl' | 'tokenName'>`) rather than a full connection, so `login` can reuse it before any connection exists.
- **On SonarQube Cloud, `sonar auth login` requires organization membership.** `--org`, `--with-token`, a key found in project config, and a hand-typed key use `OrganizationsClient.checkMembership()`. It searches the token's member organizations across all pages and returns `member | not_member | check_failed`. A public organization is rejected when the token has no membership. Keys picked from the membership menu are not re-checked because the server supplied them. SonarQube Server has no organizations, so `--org` is dropped up front on a Server connection and `resolveOrganization()` returns `undefined` there. A nonmember `--org` aborts. A nonmember key in project config falls through to the membership picker on any stdin, because a single membership needs no prompt. If the token has no memberships, login fails before showing a key prompt. A nonmember hand-typed key is warned about and asked again only on a TTY, bounded by `MAX_ORGANIZATION_ATTEMPTS`; piped input aborts. `check_failed` always aborts so an API failure cannot look like absent membership. When login fails, it revokes a newly minted token (`discardGeneratedToken`). A reused keychain token or one pasted by hand is left alone. Membership validation runs after token generation because the check needs that token.

Project discovery debug logs identify unsuccessful shared config, known mapping, local config, and git remote binding lookups. They distinguish skipped remote lookups from unresolved bindings. These diagnostics do not change source priority or the `silent` output contract.

`DiscoveredProject.gitRemoteBindingNotFound` is true only when an authenticated git-remote lookup succeeds with no bindings. Failed, skipped, ambiguous, and malformed responses do not set this signal. An unconfigured git repository then shows the fixed `sonar link <projectKey>` hint once per session while the user is logged in. No remote, no credentials, a lookup error, or SubagentStart remains silent.

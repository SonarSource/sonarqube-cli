# Harbor benchmark

Measures how coding agents use the `sonar` CLI, with [Harbor](https://docs.harborframework.com). Each directory in `tasks/` is a Harbor task: the agent works in a Docker container, a verifier writes the reward.

Run locally (Docker required, Harbor installed with `uv tool install harbor`):

```bash
harbor run --path benchmarks/harbor/tasks --agent claude-code --model anthropic/claude-sonnet-5-5 --jobs-dir /tmp/harbor-jobs --job-name local --ve EXPECTED_INTEGRATION=claude-code --ve PROMPT_HOOK=claude-prompt-submit --ve FILE_HOOK=claude-pre-tool-use
bun benchmarks/harbor/report/summarize-job.ts linux=/tmp/harbor-jobs/local
```

Local Docker runs read the Sonar credentials from `HB_SONAR_TOKEN` and `HB_SONAR_ORG` (export them from `SONARQUBE_CLI_TOKEN` and `SONARQUBE_CLI_ORG`). The task Dockerfiles write the `sonarsource` organization in the fixture repository, so a local Docker run needs `HB_SONAR_ORG=sonarsource`. `HB_SONAR_SERVER` and `HB_SONAR_API_URL` default to production SonarQube Cloud; the CI workflow sets them to staging, with the `sonarlint-it` org. The `--ve` flags give the verifier the integration and hook names to expect (other agents use their own names). `[verifier.env]` in a task's `task.toml` gives the verifier the Sonar token, organization and server URLs it needs to compute the expected answer.

In CI, run the `Harbor Benchmark` workflow manually (`workflow_dispatch` only). The agents and their models come from `strategy.matrix.agent` (`claude-code` with Anthropic models through `ANTHROPIC_API_KEY`, `codex` with OpenAI models through the `HB_OPENAI_API_KEY` repository secret), and a manual run starts one job per OS, task, agent, model and attempt, with one trial each. The report shows the agent and the model of each trial. To add an agent, give it a case in `scripts/run-isolated.sh` (install, expected integration, hooks) and in `ci/enable-hooks.sh`. The runner is fresh for every task, so nothing a task installs can leak into another. Running several trials per job would make them share the runner, so `~/.sonar`, `~/.claude` and `~/.codex` would have to be reset between trials first. Each job uploads its Harbor jobs directory, and the report job merges them per OS into the run summary.

In CI both Linux and macOS run without containers: the runner is the sandbox. The Linux runners have no Docker daemon, and macOS has no containers, so the workflow runs `scripts/run-isolated.sh`, which uses `environments/host_environment.py` (`--env host_environment:HostEnvironment`). The agent runs as the `nobody` user, which has no `sudo`, so it cannot read the runner user's processes, the OIDC token request variables or the Vault role. The script creates `/app`, `/logs`, `/tests`, `/solution` and `/installed-agent` (where Harbor puts the home of Codex) (`sudo mkdir` on Linux, `/etc/synthetic.d` symlinks on macOS), installs Harbor, `sonar` and the agent under the agent's own home, and refuses to start if the agent user can run `sudo`. The environment wipes those directories at the start of every trial and refuses to start unless `GITHUB_ACTIONS` or `HARBOR_HOST_ENVIRONMENT_ALLOW` is set. The task's `environment/Dockerfile` is only used for local runs with the default Docker environment: on the host, `environment/setup-host.sh` does its job (it runs at the start of every trial, after the wipe, which is why it cannot be a workflow step). It rebuilds the fixture repository in `/app` with `ci/init-app-repo.sh`, which takes the organization from `HB_SONAR_ORG` (the Dockerfiles write `sonarsource` instead). The secrets tasks also run `ci/enable-hooks.sh`, which installs the hooks with `sonar integrate` and copies them where Harbor makes the agent read them (`/app/.claude/settings.json` for Claude Code, `/installed-agent/codex-home` for Codex), because Harbor starts both with their own config directory. The `HB_` prefix only hides the variable names from the agent: tasks map the ones they need in `[environment.env]` (`HB_SONAR_TOKEN` becomes `SONARQUBE_CLI_TOKEN`), and `PORTKEY_API_KEY` has no prefix. The agent can read all of them, so the protection is the scope and expiry of the credentials. Claude Code reaches the model through Portkey: `run-isolated.sh` builds `ANTHROPIC_BASE_URL` and the `x-portkey-*` headers from the `PORTKEY_API_KEY` variable, which the workflow reads from the `HB_CLAUDE_PORTKEY_API_KEY` repository secret. Every `sonar` call is written to `/logs/sonar-calls.log` by `ci/sonar-wrapper.sh`, which `run-isolated.sh` installs as `~/.local/bin/sonar`, ahead of the real binary in the agent's `PATH` (each task's `environment/sonar-wrapper.sh` is a copy of it for Docker). Windows is not covered: Harbor 0.25.0 does not support `claude-code` in Windows containers.

The report takes pass/fail from the verifier reward (`1` = pass) and tokens, cost and steps from the ATIF `agent/trajectory.json` of each trial. The exit code is non-zero when any task is not `PASS`.

Nothing is published before it is scanned. After `run-isolated.sh`, each benchmark job runs `ci/scan-secrets.py` over the collected `harbor-jobs` directory, as the runner user and outside the agent's sandbox, and the report job runs it over the report text before it reaches the run summary. The script scans a copy of the files in which every name gets a `.txt` suffix (the scanner skips `.md` and `.html` by default) and the values listed in `ci/known-secrets.txt` are replaced by a filler of the same length. It runs the `sonar-secrets` binary that `sonar analyze secrets` installs, with `--max-file-size=0` and `--disable-test-file-detection`, because by default the scanner silently skips files over 1 MB and files that look like tests. `ci/known-secrets.txt` holds one public fake value per line, the ones the `secrets-context--*` tasks plant on purpose: add a line there when a task plants a new one. Any other finding is a leak. The script replaces the reported ranges, and the literal values of `SONARQUBE_CLI_TOKEN` and `PORTKEY_API_KEY` with `[REDACTED]`, scans again, and removes every file that still has a finding. A leak always fails the job, and `secrets-leak.json` next to the trial makes the report show `LEAK` instead of `PASS`. The log shows only file, line and rule key. The CLI is installed in a separate step without secrets. The benchmark-job scan step has `secrets.HB_SONAR_TOKEN` (as `SONARQUBE_CLI_TOKEN`) and `secrets.HB_CLAUDE_PORTKEY_API_KEY` (as `PORTKEY_API_KEY`) in its own `env:`. The report-job scan step has only the token, because the report job reads artifacts that were already scanned and redacted, so only the report text is scanned there. Both set `DO_NOT_TRACK=1`.

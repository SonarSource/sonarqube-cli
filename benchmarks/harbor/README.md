# Harbor benchmark

Measures how coding agents use the `sonar` CLI, with [Harbor](https://docs.harborframework.com). Each directory in `tasks/` is a Harbor task: the agent works in a Docker container, a verifier writes the reward.

Run locally (Docker required, Harbor installed with `uv tool install harbor`):

```bash
harbor run --path benchmarks/harbor/tasks --agent claude-code --model anthropic/claude-sonnet-5-5 --jobs-dir /tmp/harbor-jobs --job-name local --ve EXPECTED_INTEGRATION=claude-code --ve PROMPT_HOOK=claude-prompt-submit --ve FILE_HOOK=claude-pre-tool-use
bun benchmarks/harbor/report/summarize-job.ts linux=/tmp/harbor-jobs/local
```

Local Docker runs read the Sonar credentials from `HB_SONAR_TOKEN` and `HB_SONAR_ORG` (export them from `SONARQUBE_CLI_TOKEN` and `SONARQUBE_CLI_ORG`). The task Dockerfiles write the `sonarsource` organization in the fixture repository, so a local Docker run needs `HB_SONAR_ORG=sonarsource`. `HB_SONAR_SERVER` and `HB_SONAR_API_URL` default to production SonarQube Cloud; the CI workflow sets them to staging, and reads the Sonar token, organization and server URL from the Vault path `development/kv/data/devex-harbor-sqc`. The `--ve` flags give the verifier the integration and hook names to expect (other agents use their own names). `[verifier.env]` in a task's `task.toml` gives the verifier the Sonar token, organization and server URLs it needs to compute the expected answer.

In CI, run the `Harbor Benchmark` workflow manually (`workflow_dispatch` only). The form asks for one checkbox per task, the number of attempts (5 to 10) and a `reference` box that marks the run as the new reference run. The agent is fixed to Claude Code with Sonnet 5.5 on Linux (`AGENT` in `ci/plan-matrix.py`), with one job per task and attempt. The `plan` job turns the form into the job matrix with `ci/plan-matrix.py` and fails with a clear message when the number of attempts is out of range, when no task is checked, or when the `reference` box is checked without all the tasks. To add a task, add its checkbox to the workflow, and the script fails if a task folder has no checkbox. Also add a `description.md` next to its `instruction.md` (see below): `report/build-site.ts` fails when it is missing. `claude-code` uses Anthropic models through Portkey: `run-isolated.sh` points `ANTHROPIC_BASE_URL` at the local Portkey proxy (`scripts/portkey-proxy.py`), which adds the key from the Vault path `development/kv/data/devex-harbor-claude`; the agent never receives the key. `codex` uses OpenAI models through Portkey: the key in the Vault path `development/kv/data/devex-harbor-codex` is a Portkey key, not an OpenAI key, and `ci/codex-portkey.toml` points Codex at the same local proxy. The Sonar organization and URL come from the Vault path `development/kv/data/devex-harbor-sqc`. The token of that path is the read-only token: the agent no longer receives it (it gets a per-run token, see below), and the workflow no longer reads its token, only the organization and the URL. The form only runs Claude Code: Codex support stays in `scripts/run-isolated.sh` and `ci/enable-hooks.sh` but cannot be chosen, and running it again means changing `AGENT` in `ci/plan-matrix.py` and restoring an agent input in the workflow. The trajectory page shows the agent and the model of each trial. To add an agent, give it a case in `scripts/run-isolated.sh` (install, expected integration, hooks) and in `ci/enable-hooks.sh`. The runner is fresh for every task, so nothing a task installs can leak into another. Running several trials per job would make them share the runner, so `~/.sonar`, `~/.claude` and `~/.codex` would have to be reset between trials first. Each job uploads its Harbor jobs directory, and the report job merges them per OS into the run summary.

In CI the benchmark runs on Linux without containers: the runner is the sandbox. The Linux runners have no Docker daemon, so the workflow runs `scripts/run-isolated.sh`, which uses `environments/host_environment.py` (`--env host_environment:HostEnvironment`). The agent runs as the `nobody` user, which has no `sudo`, so it cannot read the runner user's processes, the OIDC token request variables or the Vault role. The script creates `/app`, `/logs`, `/tests`, `/solution` and `/installed-agent` with `sudo mkdir` (Harbor puts the home of Codex in `/installed-agent`), installs Harbor, `sonar` and the agent under the agent's own home, and refuses to start if the agent user can run `sudo`. The environment wipes those directories at the start of every trial and refuses to start unless `GITHUB_ACTIONS` or `HARBOR_HOST_ENVIRONMENT_ALLOW` is set. The task's `environment/Dockerfile` is only used for local runs with the default Docker environment: on the host, `environment/setup-host.sh` does its job (it runs at the start of every trial, after the wipe, which is why it cannot be a workflow step). It rebuilds the fixture repository in `/app` with `ci/init-app-repo.sh`, which takes the organization from `HB_SONAR_ORG` (the Dockerfiles write `sonarsource` instead). The secrets tasks also run `ci/enable-hooks.sh`, which installs the hooks with `sonar integrate` and copies them where Harbor makes the agent read them (`/app/.claude/settings.json` for Claude Code, `/installed-agent/codex-home` for Codex), because Harbor starts both with their own config directory. The `HB_` prefix only hides the variable names from the agent: tasks map the ones they need in `[environment.env]` (`HB_SONAR_TOKEN` becomes `SONARQUBE_CLI_TOKEN`). The agent can read all of them, so the protection is the scope and expiry of the credentials. The Portkey key is not one of them: `scripts/portkey-proxy.py` runs as the runner user, adds the key to each request and forwards only the model paths, and the agent reaches it at `127.0.0.1:8787`. Each run also gets its own SonarQube token, so the agent never receives a long-lived one: `scripts/sonar-run-token.py` creates an organization token with only the Browse role (`user`) on the benchmark project, valid for six hours, and the workflow's `Revoke the run token` step deletes it, even when the benchmark failed. It authenticates with `HB_SONAR_ADMIN_TOKEN` (Vault path `development/team/sonarlint/kv/data/sonarcloud-it`), which only the runner user holds: it is not in `RUN_ENV`. Every `sonar` call is written to `/logs/sonar-calls.log` by `ci/sonar-wrapper.sh`, which `run-isolated.sh` installs as `~/.local/bin/sonar`, ahead of the real binary in the agent's `PATH` (each task's `environment/sonar-wrapper.sh` is a copy of it for Docker). Windows is not covered: Harbor 0.25.0 does not support `claude-code` in Windows containers.

The report takes pass/fail from the verifier reward (`1` = pass) and tokens, cost and steps from the ATIF `agent/trajectory.json` of each trial. The exit code is non-zero when any task is not `PASS`.

Nothing is uploaded before the run token is revoked. The workflow step `Revoke the run token` runs `run-isolated.sh revoke` after the benchmark, even when the benchmark failed, and the `Upload Harbor jobs` step runs only if that revocation succeeded. A run token that was printed by the agent is therefore already deleted when the artifacts leave the runner, and the report jobs read only those artifacts.

The trajectories are read on the SIP site (see below): each trial has its own page. The task titles and the check sentences come from `report/tasks.ts`.

The release report turns a run into data. The `report` job builds it with `report/run-json.ts` (below). Every run is published: the `publish` job runs whenever the release report was built and uploaded, even if some trials failed, so a regression stays in the history. SIP replaces the whole site at each upload, so the job rebuilds the full site every time: `report/sip.sh pull <dir>` downloads what is published (`index.json`, then the runs it lists), `report/build-site.ts <published dir> <release-report dir> <out dir>` adds this run, and `report/sip.sh push <dir>` zips the site and publishes it. The site holds the reference run (the one made with the stable CLI) in full, the 10 latest other runs in full (the oldest leaves), and for each former reference only its `run.json`, with one file per trial to stay under the SIP limits (10 MB per served file, 50 MB per upload; `push` checks both). When a run is marked as the reference, the previous reference becomes a former reference. `build-site.ts` also replaces anything that looks like a GitHub, SonarQube, AWS or Anthropic token in the trial files of the new run with `[redacted]`: SIP runs a SonarQube Cloud analysis on the pull request of every upload, and a token-shaped text in an agent output (the example token that `sonar integrate` prints, for instance) fails its quality gate.

The evolution page (`report/evolution-page-template.html`, copied to the site root by `build-site.ts`) reads `index.json`, the `run.json` of the reference run and the `references/<id>.json` of the former references with `fetch`, and draws one column per reference, ordered by date: a box plot and the dots of the trials for one task and one measure, chosen in the side bar. Clicking a column shows that reference below the chart, with its trials. It computes the medians in the page, so a former reference needs nothing more than its `run.json`.

```
index.json            reference, latest runs, former references (run ids)
index.html            home page (report/home-page.ts and home-page-template.html): the reference, the latest runs, one run compared with the reference
run.html              the page of one run, opened as run.html?run=<run id>
trial.html            the page of one trial, opened as trial.html?run=<run id>&trial=<trial id>
evolution.html        the evolution page, read from index.json and the run files
tasks.json            the description of every task (from tasks/<task>/description.md)
task.html             the page that shows tasks.json, task.html?task=<task>
runs/<run id>/run.json, runs/<run id>/trials/<trial id>.json
references/<run id>.json
```

The two pages are static files (`report/run-page-template.html` and `trial-page-template.html`) that read the JSON files with `fetch`, because SIP does not serve an `index.html` for a folder below the root. The run page shows, for each task, the trials of the run as dots and a box plot of the run next to a box plot of the reference, one measure at a time, chosen in a side bar next to each chart (time, tokens, steps), with a tooltip on the dots and the boxes. Clicking a task block greys it and lists its trials: each one is a bar for the measure it is sorted by (number, time, tokens or steps), with an option to keep only the trials that did not pass. Each dot and each bar links to the trial page (`trial-page-template.html`), which reads the trial file and lists the agent steps with their commands and outputs. The reference run is not compared with itself.

Each task describes itself in `tasks/<task>/description.md`, which `build-site.ts` reads with the `instruction.md` of the task (key-shaped texts are replaced with `[redacted]`) to write `tasks.json`. The file has a fixed shape, and the build fails with a message when a title is missing or out of order, when a check line is malformed, or when the checks of the new run do not match the keys the verifier wrote (`trajectory_present` and `trajectory_ok` are not checks):

```
# <the question the task answers>

## What it tests
## Starting point
## What counts as success
## Checks
- `<key written by tests/test.sh>`: <one sentence>
```

Text between backticks is shown as code. Copy an existing `description.md` to start a new one.

The `index.json` published on SIP is the only history, and the job needs the `SIP_PLATFORM_TOKEN` repository secret (a personal SIP token, valid one year).

`report/run-json.ts --cli-version <v> --run-id <id> --date <iso> --attempts <n> [--reference] --out <dir> <runDir>` writes the data of the future SIP site (`schemaVersion` 2): `run.json` holds the run (CLI version, date, attempts per task, reference flag) and one summary per trial (task, agent, model, status, agent seconds, step count, tokens), and `trials/<trial id>.json` holds the reduced trajectory of one trial (messages, commands, outputs cut at 2000 characters) and its verifier checks. The `report` job calls it with the `attempts` and `reference` inputs of the form.

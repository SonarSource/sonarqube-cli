# Harbor benchmark

Measures how coding agents use the `sonar` CLI, with [Harbor](https://docs.harborframework.com). Each directory in `tasks/` is a Harbor task: the agent works in a Docker container, a verifier writes the reward.

Run locally (Docker required, Harbor installed with `uv tool install harbor`):

```bash
harbor run --path benchmarks/harbor/tasks --agent claude-code --model anthropic/claude-sonnet-5-5 --jobs-dir /tmp/harbor-jobs --job-name local --ve EXPECTED_INTEGRATION=claude-code --ve PROMPT_HOOK=claude-prompt-submit --ve FILE_HOOK=claude-pre-tool-use
bun benchmarks/harbor/report/summarize-job.ts linux=/tmp/harbor-jobs/local
```

Local Docker runs read the Sonar credentials from `HB_SONAR_TOKEN` and `HB_SONAR_ORG` (export them from `SONARQUBE_CLI_TOKEN` and `SONARQUBE_CLI_ORG`). The task Dockerfiles write the `sonarsource` organization in the fixture repository, so a local Docker run needs `HB_SONAR_ORG=sonarsource`. `HB_SONAR_SERVER` and `HB_SONAR_API_URL` default to production SonarQube Cloud; the CI workflow sets them to staging, with the `sonarlint-it` org. The `--ve` flags give the verifier the integration and hook names to expect (other agents use their own names). `[verifier.env]` in a task's `task.toml` gives the verifier the Sonar token, organization and server URLs it needs to compute the expected answer.

In CI, run the `Harbor Benchmark` workflow manually (`workflow_dispatch` only). The agents and their models come from `strategy.matrix.agent`, and a manual run starts one job per OS, task, agent, model and attempt, with one trial each. `claude-code` uses Anthropic models through Portkey: `run-isolated.sh` builds `ANTHROPIC_BASE_URL` and the `x-portkey-*` headers from the `HB_CLAUDE_PORTKEY_API_KEY` repository secret. `codex` uses OpenAI models through Portkey: the `HB_OPENAI_PORTKEY_API_KEY` repository secret is a Portkey key, not an OpenAI key, and `ci/codex-portkey.toml` points Codex at Portkey. The Sonar token comes from `HB_SONAR_TOKEN`. The report shows the agent and the model of each trial. To add an agent, give it a case in `scripts/run-isolated.sh` (install, expected integration, hooks) and in `ci/enable-hooks.sh`. The runner is fresh for every task, so nothing a task installs can leak into another. Running several trials per job would make them share the runner, so `~/.sonar`, `~/.claude` and `~/.codex` would have to be reset between trials first. Each job uploads its Harbor jobs directory, and the report job merges them per OS into the run summary.

Codex does not run on macOS (`strategy.matrix.exclude`). Harbor 0.25.0 gives `chown` the numeric id of the agent user, and macOS rejects the id of `nobody` (4294967294).

In CI both Linux and macOS run without containers: the runner is the sandbox. The Linux runners have no Docker daemon, and macOS has no containers, so the workflow runs `scripts/run-isolated.sh`, which uses `environments/host_environment.py` (`--env host_environment:HostEnvironment`). The agent runs as the `nobody` user, which has no `sudo`, so it cannot read the runner user's processes, the OIDC token request variables or the Vault role. The script creates `/app`, `/logs`, `/tests`, `/solution` and `/installed-agent` with `sudo mkdir` on Linux and `/etc/synthetic.d` symlinks on macOS (Harbor puts the home of Codex in `/installed-agent`), installs Harbor, `sonar` and the agent under the agent's own home, and refuses to start if the agent user can run `sudo`. The environment wipes those directories at the start of every trial and refuses to start unless `GITHUB_ACTIONS` or `HARBOR_HOST_ENVIRONMENT_ALLOW` is set. The task's `environment/Dockerfile` is only used for local runs with the default Docker environment: on the host, `environment/setup-host.sh` does its job (it runs at the start of every trial, after the wipe, which is why it cannot be a workflow step). It rebuilds the fixture repository in `/app` (`ci/init-app-repo.sh`, the same content as the Dockerfile). The secrets tasks also run `ci/enable-hooks.sh`, which installs the hooks with `sonar integrate` and copies them where Harbor makes the agent read them (`/app/.claude/settings.json` for Claude Code, `/installed-agent/codex-home` for Codex), because Harbor starts both with their own config directory. Variables named `HB_*` (the Sonar token and organization) are hidden from the agent: tasks map the ones they need in `[environment.env]`. Every `sonar` call is written to `/logs/sonar-calls.log` by `ci/sonar-wrapper.sh`, which `run-isolated.sh` installs as `~/.local/bin/sonar`, ahead of the real binary in the agent's `PATH` (each task's `environment/sonar-wrapper.sh` is a copy of it for Docker). Windows is not covered: Harbor 0.25.0 does not support `claude-code` in Windows containers.

The report takes pass/fail from the verifier reward (`1` = pass) and tokens, cost and steps from the ATIF `agent/trajectory.json` of each trial. The exit code is non-zero when any task is not `PASS`.
